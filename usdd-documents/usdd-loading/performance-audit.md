### 复测结论

- **CDN 效果最显著的是 TTFB**：从 ~1,300ms 降至 ~535ms，已达到良好标准（< 600ms）
- **静态资源（React / antd / echarts 等）全部命中 CDN 缓存**，单个文件加载从数百毫秒压缩到 60~150ms
- **首屏渲染仍偏慢**：两站 First Paint 均在 2~3 秒，仍超出 Google 良好基准（< 1,800ms）
- **根本瓶颈未变**：主包 JS 体积过大（~1.6MB），CDN 加快传输，但浏览器解析执行耗时无法通过 CDN 解决
- **骨架屏设计价值仍然成立**：即使在 WiFi 下，2~3 秒的空白等待期依然存在
- **Slow 3G 几乎无改善**：带宽是硬瓶颈（约 62KB/s），CDN 无法绕开，弱网环境的根本解法是减小 JS 包体积
- **网速越快，CDN 效果越明显**：4G 提升约 25%，WiFi 提升 50~67%；CDN 的核心价值在好网络环境下

## 7. 总结与问题诊断

### 主要瓶颈

1. **JS 包体积过大**  
   usdd.io 主包 813 KB（压缩）/ 1.6 MB（原始）——这是导致低速网络极慢的核心原因。  
   行业建议首屏 JS < 200 KB。

2. **app.usdd.io 额外引入 Web3 SDK**  
   TronWeb + ethers.js 合计估算 1.2 MB+，在 3G 环境下加载耗时超 30 秒，严重影响用户体验。

3. **服务器 TTFB 偏高**  
   ~1.3 s 的服务器响应时间说明 CDN 节点覆盖或服务器配置有优化空间（目标 < 600 ms）。  
   > ✅ **已改善（2026-04-15）**：接入 CDN 后 TTFB 降至 ~535ms，此问题已基本解决。

4. **首屏无有效 Loading 状态**  
   在 JS 全部加载前，用户看到的是空白或未渲染完成的骨架，体感等待时间更长。

### 改善方向（按优先级）

| 优先级 | 方向 | 预期收益 |
|--------|------|----------|
| 🔴 高 | 代码分包（Code Splitting）——按路由懒加载 | 首屏 JS 减少 50~70% |
| 🔴 高 | Web3 SDK 按需引入，或延迟加载 | app 端减少 1~2s |
| 🟡 中 | CDN 节点优化 / 启用 HTTP/2 Push | TTFB 降至 < 600ms |
| 🟡 中 | 增加骨架屏 / Loading 占位 | 体感等待降低 |
| 🟢 低 | 开启 Brotli 压缩 | JS 包额外减少 15% |
