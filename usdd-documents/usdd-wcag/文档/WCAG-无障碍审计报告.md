## 什么是 WCAG 无障碍设计

WCAG（Web Content Accessibility Guidelines，网页内容无障碍指南）是国际公认的数字产品无障碍标准，由 W3C 制定，目前主流版本为 **WCAG 2.1**。

它解决的核心问题是：**当用户因为视觉、听觉、运动或认知上的限制，无法按照"正常方式"使用产品时，产品是否依然可用？**

这些用户包括但不限于：
- **失明/弱视用户** — 使用屏幕阅读器（如 VoiceOver、NVDA）浏览网页，完全依赖文字描述和语义结构
- **肢体障碍用户** — 无法使用鼠标，只能通过键盘 Tab / Enter / Space 键操作
- **色觉障碍用户** — 无法区分颜色对比度不足的文字与背景
- **认知障碍用户** — 需要清晰的结构和一致的交互逻辑

WCAG 2.1 按合规程度分为三个等级：

| 等级 | 含义 | 实际要求 |
|-----|-----|---------|
| **A**（基础）| 最低门槛，不达标代表产品对部分用户完全不可用 | 必须满足 |
| **AA**（推荐）| 主流法规（欧盟 EN 301 549、美国 Section 508）的法律要求门槛 | 行业标准 |
| **AAA**（卓越）| 最高标准，适用于对无障碍有专项承诺的产品 | 可选努力 |

> 本次审计目标为达到 **WCAG 2.1 AA 级**，这也是全球大多数国家数字产品合规的基线要求。

## WCAG 四大原则与 USDD 现状总览

WCAG 由 4 个核心原则构成，简称 **POUR**。下表梳理了 USDD 在每个维度的现状、发现的主要问题，以及修复所需的资源。

| 维度 | 核心问题是什么 | USDD 现状 | 发现的主要问题 | 解决方案 | 所需资源 |
|-----|-------------|:--------:|-------------|---------|:-------:|
| **P — 可感知（Perceivable）**<br>信息必须能被用户感知，不能只依赖视觉 | 图片有没有文字说明？颜色对比够不够？ | 🔴 不合格 | 28 个交易所图标链接无 alt 文字；社交图标链接无名称；主按钮对比度 3.80:1（要求 4.5:1）；次要文字使用 60% 透明白色风险偏高 | 为所有纯图标的链接和按钮补充文字描述；调整按钮颜色至对比度达标；在设计稿中明确颜色透明度使用规则 | 设计师（颜色 Token 调整）<br>+ 前端（补充 aria-label / alt） |
| **O — 可操作（Operable）**<br>所有功能必须能通过键盘完成，不能只依赖鼠标 | 能用 Tab 键到达每个按钮和链接吗？焦点在哪里看得见吗？ | 🔴 不合格 | 全局 CSS 清除了所有链接的焦点样式（`a:focus { outline:0 }`）；导航下拉菜单是 `<div>` 无法用键盘触达；行动入口用 `<p>` 标签实现，Tab 键无法到达；轮播容器焦点被清除 | 恢复链接焦点样式；将交互性 `<div>` 改为 `<button>` 或 `<a>`；在设计稿中定义所有交互组件的 Focus State 视觉规范 | 设计师（Focus State 设计规范）<br>+ 前端（修复语义标签和 CSS） |
| **U — 可理解（Understandable）**<br>内容和操作逻辑必须清晰可理解 | 页面结构清晰吗？表单告诉用户该填什么吗？删除线表达的意思用户都能理解吗？ | 🟠 部分合格 | 标题层级严重混乱（H2→H5→H1 / H2→H6）；表单输入框只有 placeholder 没有真正的标签；轮播分页按钮名称为无意义的数字；Stability Fee 删除线价格无语义说明 | 重新规划页面标题层级（从 H1 开始逐级递进）；为表单控件设计明确的标签样式；为特殊状态（删除线、折扣标签）补充语义方案 | 设计师（页面结构重规划、表单 Label 视觉设计）<br>+ 前端（标题标签修正、`<label>` 关联） |
| **R — 健壮（Robust）**<br>代码结构必须足够规范，让各种辅助技术都能正确解析 | 屏幕阅读器能正确识别每个交互元素的类型和状态吗？ | 🔴 不合格 | 导航菜单无 `role` / `aria-expanded` 声明；回到顶部按钮无 `aria-label`；邮件地址被逐字符拆分影响朗读；Figma 设计系统未定义 Focus / Disabled 状态的颜色 Token，设计与开发缺乏统一标准 | 所有自定义交互元素补充 ARIA 属性；在 Figma 中建立包含 Focus State 和 Disabled State 的完整组件规范；与前端约定组件状态的实现标准 | 设计师（完善 Design System 组件状态规范）<br>+ 前端（补充 ARIA 属性） |

### 问题 1｜所有链接的键盘焦点样式被全局清除

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io + app.usdd.io |
| **WCAG 条款** | SC 2.4.7 焦点可见（Focus Visible） |
| **影响用户** | 所有键盘用户、运动障碍用户 |

**问题描述**

两个网站的全局 CSS 中存在以下规则，完全清除了所有链接的焦点指示器：

```css
a:focus { outline: 0px; }
```

键盘用户通过 Tab 键导航时，完全看不到焦点停在哪里，等同于在屏幕上操作但看不到鼠标光标。当前按钮有正确的焦点样式（app 使用浅绿色 outline），但链接没有，行为不一致。

**解决方案**

- **方案 A（推荐）— 用 `:focus-visible` 替代 `:focus`，自定义品牌焦点样式**
  鼠标点击不显示焦点环（更干净的视觉），键盘操作时才显示。焦点色与品牌绿保持一致。
  ```css
  /* 移除原有的全局清除规则 */
  /* a:focus { outline: 0px; }  ← 删除这行 */

  a:focus-visible {
    outline: 2px solid #26A17B; /* 品牌绿 */
    outline-offset: 3px;
    border-radius: 2px;
  }
  ```
  > 所需资源：**设计师**定义焦点色 Token（建议用品牌绿），**前端**修改 CSS

- **方案 B — 仅移除清除规则，保留浏览器默认焦点样式**
  成本最低，一行删除即可生效。视觉上是蓝色虚线/蓝色 outline，不符合品牌但功能正确。
  > 所需资源：**前端**独立完成

- **方案 C — 在现有组件库（Ant Design）主题中统一配置焦点色**
  通过 AntD 的 ConfigProvider 统一设置，确保链接和按钮焦点样式一致。
  > 所需资源：**前端**独立完成

### 问题 2｜交易所图标链接无任何可访问名称（共 28 个）

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io 首页 "USDD Markets" 区域 |
| **WCAG 条款** | SC 1.1.1 非文字内容 / SC 4.1.2 名称、角色、值 |
| **影响用户** | 视障用户（屏幕阅读器）|

**问题描述**

HTX、Bybit、Gate.io、MEXC 等所有交易所跳转链接只有图标，无 `alt` 文字也无 `aria-label`。屏幕阅读器读到的是连续 28 个匿名链接，用户无从判断去哪里。同一组链接走马灯循环重复了两遍，产生大量重复无名链接。

**解决方案**

- **方案 A（推荐）— 给每个 `<img>` 补充 `alt` 属性**
  直接在图片标签上添加交易所名称，无需改动布局。
  ```html
  <!-- 修改前 -->
  <img src="htx-logo.png" />
  <!-- 修改后 -->
  <img src="htx-logo.png" alt="HTX" />
  ```
  > 所需资源：**前端**独立完成（批量处理）

- **方案 B — 给 `<a>` 标签添加 `aria-label`**
  描述性更强，可在链接名称中加入跳转说明。
  ```html
  <a href="https://www.htx.com/..." aria-label="在 HTX 交易 USDD">
    <img src="htx-logo.png" alt="" />
  </a>
  ```
  > 所需资源：**前端**独立完成

- **方案 C — 图标旁加可见文字标签（对所有用户友好）**
  在设计上于 logo 下方增加交易所名称文字，对所有用户都更清晰，同时解决无障碍问题。
  > 所需资源：**设计师**更新设计稿布局，**前端**实现

### 问题 3｜表单输入框无标签关联

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io Yield Simulator 区域 |
| **WCAG 条款** | SC 1.3.1 信息和关系 / SC 4.1.2 名称、角色、值 |
| **影响用户** | 视障用户（屏幕阅读器）|

**问题描述**

| 输入框 | 现状 |
|-------|-----|
| 金额输入框 `placeholder="Enter an amount"` | 只有 placeholder，无 `<label>` 或 `aria-label` |
| 搜索框 `type="search"` | 无任何标签 |

Placeholder 是提示文字不是标签，用户开始输入后它会消失，屏幕阅读器用户从此失去对输入框用途的感知。

**解决方案**

- **方案 A（推荐）— 设计上增加可见 Label，视觉与语义同步**
  在输入框上方或左侧增加明确的标签文字（如 "Amount" / "金额"），用 `<label>` 标签关联。对所有用户都更清晰，同时解决无障碍问题。
  ```html
  <label for="amount-input">Amount</label>
  <input id="amount-input" type="text" placeholder="Enter an amount" />
  ```
  > 所需资源：**设计师**补充 Label 视觉方案，**前端**实现关联

- **方案 B — 保持现有视觉，添加 `aria-label`（不改变界面外观）**
  无需改动设计，仅在代码层添加不可见的标签。
  ```html
  <input type="text" aria-label="输入金额（USDD）" placeholder="Enter an amount" />
  ```
  > 所需资源：**前端**独立完成

- **方案 C — 用 `aria-labelledby` 指向页面中已有的文字**
  如果输入框附近已有说明文字，可直接将其关联为标签，不需要新增元素。
  > 所需资源：**前端**独立完成

### 问题 4｜"回到顶部"按钮无可访问名称

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io |
| **WCAG 条款** | SC 4.1.2 名称、角色、值 |
| **影响用户** | 视障用户（屏幕阅读器）|

**问题描述**

页面右下角的 back-to-top 按钮仅包含 SVG 图标，无任何文字描述。屏幕阅读器用户遇到一个没有名字的按钮，不知道它的用途。

**解决方案**

- **方案 A（推荐）— 添加 `aria-label`**
  最简单直接，不影响视觉。
  ```html
  <button class="back-top" aria-label="返回顶部">
    <svg>...</svg>
  </button>
  ```
  > 所需资源：**前端**独立完成（1 行代码）

- **方案 B — 添加视觉隐藏文字（`.sr-only`）**
  在按钮内加入只有屏幕阅读器能读到的文字，视觉上不可见。
  ```html
  <button class="back-top">
    <svg aria-hidden="true">...</svg>
    <span class="sr-only">返回顶部</span>
  </button>
  ```
  > 所需资源：**前端**独立完成

- **方案 C — 按钮旁增加可见的"Top"文字标签**
  将悬浮按钮设计成图标 + 文字组合，对所有用户可见。
  > 所需资源：**设计师**更新组件视觉，**前端**实现

### 问题 5｜导航交互区域使用 `<div>` 实现，无法通过键盘操作

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io（Developer / Transparency / Community 下拉）+ app.usdd.io（Vault 导航项）|
| **WCAG 条款** | SC 4.1.2 名称、角色、值 |
| **影响用户** | 键盘用户、视障用户 |

**问题描述**

这些导航元素有 `cursor:pointer` 和点击/悬停交互，但底层是 `<div>`，缺少：
- 键盘可达性（无 `tabindex`，Tab 键跳过）
- 语义角色声明（无 `role`，屏幕阅读器不识别为可点击）
- 展开状态反馈（无 `aria-expanded`，用户不知道菜单是否打开）

**解决方案**

- **方案 A（推荐）— 将触发元素改为 `<button>` 标签**
  浏览器原生支持键盘操作（Tab 可达、Enter/Space 触发），无需额外处理。
  ```html
  <!-- 修改前 -->
  <div class="nav-item">Developer <img /></div>
  <!-- 修改后 -->
  <button class="nav-item" aria-expanded="false" aria-haspopup="true">
    Developer <img aria-hidden="true" />
  </button>
  ```
  > 所需资源：**前端**主导（需确认样式不受影响）

- **方案 B — 保留 `<div>`，补充 ARIA 属性 + 键盘事件**
  不改变标签，在现有 `<div>` 上添加角色、tabindex 和键盘监听。修改量小但需要手动处理所有键盘逻辑。
  ```html
  <div role="button" tabindex="0" aria-expanded="false" aria-haspopup="true">
    Developer
  </div>
  ```
  > 所需资源：**前端**主导

- **方案 C — 若导航项有对应落地页，直接改为 `<a>` 标签**
  如果每个导航项本身可以单独跳转，用链接语义最自然。
  > 所需资源：**前端**主导，**产品**确认跳转逻辑

### 问题 6｜行动链接使用 `<p>` 标签代替交互元素

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io "USDD Transition and Rewards" 区域 |
| **WCAG 条款** | SC 4.1.2 名称、角色、值 |
| **影响用户** | 键盘用户、视障用户 |

**问题描述**

"Migrate USDD"、"Mint USDD"、"Earn" 三个行动入口用 `<p>` 标签 + `cursor:pointer` 实现，Tab 键无法到达，屏幕阅读器不识别为可交互，Enter 键无法激活。

**解决方案**

- **方案 A（推荐）— 改为 `<a href>` 标签**
  这类入口本质是跳转链接，用 `<a>` 最准确，语义最清晰。
  ```html
  <!-- 修改前 -->
  <p style="cursor:pointer">Migrate USDD</p>
  <!-- 修改后 -->
  <a href="/migrate" class="action-link">Migrate USDD →</a>
  ```
  > 所需资源：**前端**独立完成（需确认目标 URL）

- **方案 B — 改为 `<button>` 标签**
  如果行动是触发弹窗或流程而非跳转，用 `<button>` 更准确。
  ```html
  <button class="action-link" onclick="openMigrateModal()">
    Migrate USDD
  </button>
  ```
  > 所需资源：**前端**独立完成

- **方案 C — 在现有 `<p>` 上添加 ARIA 属性（不推荐，治标不治本）**
  最小改动，但需要手动处理键盘事件，长期维护成本高。
  ```html
  <p role="link" tabindex="0" onclick="..." onkeydown="...">Migrate USDD</p>
  ```
  > 所需资源：**前端**主导（仅作临时过渡方案）

### 问题 7｜轮播分页按钮标签无意义

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io（按钮名 "1"–"6"）/ app.usdd.io（按钮名 "1"、"2"）|
| **WCAG 条款** | SC 4.1.2 名称、角色、值 |
| **影响用户** | 视障用户（屏幕阅读器）|

**问题描述**

轮播分页点按钮的名称只是数字 "1"、"2"……对屏幕阅读器用户无任何上下文，无法理解它们是轮播切换控件。

**解决方案**

- **方案 A（推荐）— 添加描述性 `aria-label` + `aria-current`**

### 问题 10｜半透明文字体系导致大面积颜色对比度失败 ⭐ 最高优先级

> 📋 **v6审计关联：这是 v6 审计在 USDD 上的核心发现，被列为 P0 紧急。**
>
> - USDD 整体 WCAG AA 色彩合规率：**仅 21%**（对比同生态 TronScan 86%、TRON-Web 67%）
> - v6 审计原文：*"USDD 无障碍灾难：79% 文字元素对比度未达 WCAG AA。根因是规范中定义的 5 档半透明文字体系"*
> - v6 整改优先级：**P0 紧急**（合规风险 + 真实用户流失）

| 项目 | 内容 |
|-----|-----|
| **影响页面** | usdd.io + app.usdd.io（全站范围）|
| **WCAG 条款** | SC 1.4.3 对比度（最低）|
| **影响用户** | 低视力用户、色觉障碍用户、强光/户外使用场景用户 |

**问题描述**

USDD 设计规范定义了一套 5 档半透明白色文字体系，用于区分文字层级。其中低透明度档位在深色背景以外的场景下严重不合规：

| 文字档位 | 颜色值 | 实测对比度（深色背景）| AA 要求 | 结论 |
|---------|-------|:------------------:|:------:|:---:|
| text-primary | `rgba(255,255,255,1.0)` | 21:1 | 4.5:1 | ✅ 通过 AAA |
| text-80 | `rgba(255,255,255,0.8)` | ~15:1 | 4.5:1 | ✅ 通过 AA |
| text-60 | `rgba(255,255,255,0.6)` | ~7:1 | 4.5:1 | ⚠️ 通过，但有背景依赖风险 |
| **text-40** | **`rgba(255,255,255,0.4)`** | **~4.0:1** | 4.5:1 | **❌ FAIL（刚好不足）** |
| **text-20** | **`rgba(255,255,255,0.2)`** | **~1.9:1** | 4.5:1 | **❌ FAIL（严重不合规）** |

**关键背景信息（来自 v6 审计）：**
- USDD 的 CSS 工程层是同生态产品中最规范的，但 WCAG 合规率却是最低的
- 这说明"代码整洁"不等于"用户可用"，问题出在**设计规范本身**定义了不合规的颜色档位
- 合规风险：欧盟 EAA 2025 已生效，美国 ADA 对金融类网站有强制要求，稳定币产品面临实际合规压力

**解决方案**

- **方案 A（推荐，与 v6 审计整改方向一致）— 废弃 text-40 / text-20，改用颜色 + 字重区分层级**
  不再依赖透明度表达文字层级，改用不同色相（如灰色系）或字重（Regular / Medium / SemiBold）来区分主次文字。这从设计规范源头解决问题，且不依赖特定背景色。
  ```
  现有层级（透明度）：
  text-primary 100% → 80% → 60% → 40% → 20%

  建议改为（色相 + 字重）：
  主要文字：#FFFFFF（白色）SemiBold
  次要文字：#B0B8C1（中灰白）Regular
  辅助文字：#7A8490（灰）Regular
  禁用文字：#4A5260（深灰）Regular  ← 不低于 4.5:1
  ```
  > 所需资源：**设计师**重新定义文字颜色 Token 体系（核心工作约 2–3 天），**前端**全局替换 CSS 变量

- **方案 B — 提高 text-40 / text-20 的透明度至安全阈值**
  将 0.4 提升至至少 0.6（对比度约 7:1），将 0.2 提升至至少 0.5（对比度约 5:1）。改动量小，但仍有背景依赖风险——若页面出现浅色区块，改后的颜色仍可能失败。
  > 所需资源：**设计师**调整 Token 值，**前端**更新 CSS 变量

- **方案 C — 添加背景色感知逻辑（工程方案，不推荐作为唯一方案）**
  在深色区块用白色透明文字，在浅色区块自动切换为深色文字。技术上可行但维护成本高，且不解决设计规范本身的问题。
  > 所需资源：**前端**独立实现（建议仅作为方案 A 的过渡补丁）
