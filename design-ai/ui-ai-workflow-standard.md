# UI/UX 设计师 AI 工作流规范

> TRON ECO Product & UI Team · v1.0 · 2026-04-08
>
> 以 UI/UX 设计师视角，定义设计师借助 Claude Code / AI 工具完成日常设计工作的标准流程、交付物要求和质量门禁。与 PM 主流程（`pm-ai-workflow-standard.md`）并行。

---

## Executive Summary

**目标**：设计师借助 AI 将重复性执行工作（线框稿生成、规范校验、标注文档、截图对比）自动化，把精力集中在「要不要」的设计决策上，而非「怎么做」的实现细节。

**分工原则**：

- **设计师做**：信息架构判断、视觉决策、走查定性、交付确认
- **AI 做**：线框稿生成、规范校验、高保真 HTML、标注文档提取、截图对比

**知识库联动**：


| AI 每次对话自动读取                           | 用途         |
| ------------------------------------- | ---------- |
| `design/USDD-component-guidelines.md` | Token、组件规范 |
| `USDD2.0/design.md`                   | 端级设计约束     |
| `shared/glossary.md`                  | 领域术语统一     |
| `USDD2.0/figma-design-index.md`       | Figma 稿件索引 |

## 一、核心原则


| #   | 原则                | 说明                                                      |
| --- | ----------------- | ------------------------------------------------------- |
| 01  | **设计师做决策，AI 做执行** | AI 生成线框、套用规范、输出标注。设计师判断「要不要」，AI 实现「怎么做」。AI 产出的一切内容都是草稿。 |
| 02  | **不允许脑补，信息不足先提问** | 信息不足时 AI 必须先提问，不自行补完布局或交互逻辑。不确定处标注「⚠️ 待确认」。             |
| 03  | **用文件沉淀，不用对话沉淀**  | 走查记录、交付包、验收报告必须写入文件。对话结束后产出不丢失。                         |
| 04  | **小步快跑，先骨架后高保真**  | 先出线框确认结构，规范校验通过后再进入高保真。不跳过 S3 门槛直接做 S4。                 |
| 05  | **走查反馈必须量化**      | 「感觉不对」不是有效反馈。必须给出「具体数值 + 具体页面 + 期望值」，AI 才能准确修改。         |

## 二、设计工作流全景

设计流程共 **7 个阶段**（S1–S7），与 PM 主流程 Phase 3–6 并行推进：

```
PM 主流程：  Phase 1 → Phase 2 → Phase 3 ──────────────── Phase 4-5 ────── Phase 6 ──→ Phase 7
                                    ↓ PRD 交付设计
设计流程：               S1 需求拆解 → S2 线框稿 → S3 规范校验 → S4 UI 稿 → S5 走查 → S6 交付包 → S7 开发验收
```

### 各阶段速览


| Stage  | 阶段     | AI 做什么                | 设计师做什么                     | 核心产出                            | 通过标准                       |
| ------ | ------ | --------------------- | -------------------------- | ------------------------------- | -------------------------- |
| **S1** | 需求拆解   | 读取 PRD，生成结构化设计简报      | 补充交互细节，确认 MVP 范围，锁定「不设计」范围 | `brief-{功能名}.md`                | 页面清单完整，异常状态覆盖，设计师 + PM 双签字 |
| **S2** | 线框稿    | 生成灰度 HTML 线框          | 审核信息层级和主流程结构               | 线框稿（过程稿）                        | 主流程零歧义，可交互元素 ≥44px         |
| **S3** | 规范校验   | 自动校验色彩/字体/圆角/间距       | 确认校验结果，一次性修复不合规项           | 校验报告（校验通过即可）                    | 总分 ≥95%，色彩/字体/圆角 100%      |
| **S4** | UI 设计稿 | 套用完整设计规范，生成高保真 HTML   | 做视觉决策，审批关键参数               | `ui-{功能名}-v{N}.html` + Figma 链接 | 色差 deltaE < 2，图标线宽统一       |
| **S5** | 走查修改   | 按量化走查反馈逐项修改，标注修改 ID   | 量化走查（数值+页面+期望），最多 3 轮      | `walkthrough-{功能名}-{日期}.md`     | 最多 3 轮，P0/P1 全部修复          |
| **S6** | 交付包    | 从代码提取数值，生成标注文档 + 切图清单 | 确认交付完整性，记录 Figma 链接        | 标注文档 + `components.css` + 切图清单  | 开发可直接使用，无需二次询问设计师          |
| **S7** | 开发验收   | 截图对比，输出差异报告           | 与 PM 共同确认还原度，签字            | `acceptance-{功能名}-{日期}.md`      | 整体还原度 ≥90%，设计师签字           |

## 三、各阶段详解

### S1 — 需求拆解

**目标**：将 PRD 转化为设计师可执行的结构化简报，在动笔前对齐范围。

**AI 协作步骤**：

1. AI 读取 `iterations/v{x.y.z}/prd-{name}.md` + `design/USDD-component-guidelines.md`
2. AI 输出设计简报草稿，包含：
  - 页面清单（每个页面名称 + 入口）
  - 组件清单（复用组件 + 新增组件）
  - 异常状态清单（空态/加载/错误/边界值）
  - 「不设计的范围」明确列出
3. 使用「用户影响 × 开发复杂度」矩阵确认 MVP 范围
4. 设计师补充细节 → **设计师 + PM 双签字**

**Prompt 模版**：

```md
请作为 UI/UX 设计师，帮我完成「需求拆解」。

输入资料：
- PRD：`/Users/luke/luke-usdd/usdd-pages/footer/usdd-footer-改版.md`
- 设计规范：`design/USDD-component-guidelines.md`

任务要求：
1. 先完整阅读 PRD，不允许脑补缺失信息
2. 输出一份结构化设计简报草稿
3. 内容维度：
   - 页面清单（页面名称 + 页面目标 + 入口）
   - 组件清单（复用组件 / 新增组件）
   - 异常状态清单（空态 / 加载 / 错误 / 边界值）
   - MVP 范围
   - 不设计的范围
   - 待确认问题
4. 对信息不足处统一标注 `⚠️ 待确认`

输出格式：
- 直接输出为 `brief-{功能名}.md` 的 Markdown 内容
- 标题清晰，列表结构化

限制：
- 不输出视觉方案
- 不进入高保真层面的颜色、样式、动效设计
- 不自行补完未在 PRD 中明确的业务规则
```

**通过标准**：

- 页面清单与 PRD 功能清单对应
- 异常状态（空/加载/错/边界）全部识别
- 「不设计的范围」已明确锁定
- 设计师 + PM 双签字

**产出**：`iterations/v{x.y.z}/brief-{功能名}.md`

### S2 — 线框稿

**目标**：用灰度低保真 HTML 验证信息层级和主流程，不涉及视觉细节。

**AI 协作步骤**：

1. AI 读取 S1 简报 + PRD 用户流程章节
2. AI 生成灰度 HTML 线框（仅用灰阶色，无品牌色，无精细排版）
3. 设计师审核：信息层级、主流程顺序、关键交互节点
4. 修改指令格式要精确：「**改什么 + 改哪里 + 改成什么**」，不接受模糊描述

**Prompt 模版**：

**A — 生成线框稿主 Prompt**

```md
请基于以下设计简报，生成 USDD 风格的 HTML 线框稿：

[粘贴 S1 输出的简报内容]

要求：
- 375px 手机尺寸
- 灰度占位色（不使用品牌色），突出结构
- 每个屏幕包含：顶部导航 + 内容区 + （可选）底部标签栏
- 包含：主流程页面 + 所有异常状态（空态 / 加载 / 错误）
- 可交互：底部抽屉、弹窗的开关效果
- 每个屏幕下方附「设计注释」说明关键决策
- 所有可交互元素尺寸必须 ≥ 44px
- 输出单文件 HTML
```

**B — 增量修改（精确指令示范）**

> 每次修改使用精确指令，说清楚「改什么、改哪里、改成什么」

```md
# ✅ 正确写法：
请修改「存入 USDD 页」的输入区域：
- 在金额输入框下方增加「预计收益」实时计算行
- 左侧标签「预计日收益」，右侧数值
- 保持现有间距规范不变

# ❌ 错误写法（不要这样）：
帮我把页面改得好看一点
```

**C — 让 AI 自检线框稿结构**

```md
请对刚刚生成的线框稿做结构检查，逐项验证：
1. 每个屏幕是否有顶部导航 + 内容区 + （可选）底部标签栏
2. 所有触控元素高度是否 ≥ 44px（在 CSS 中检查 height 值）
3. 内容区左右 margin 是否合理（参考规范）
4. 是否覆盖了简报中要求的所有异常状态
5. 底部抽屉是否有遮罩 + 抽屉本体 + JS 开关逻辑
输出格式：✅通过 / ❌不通过 + 问题位置
```

> **注意**：线框稿是过程稿，不需要保存为正式产出文件。线框稿通过后直接进入 S3。

**通过标准**：

- 主流程完整，零歧义
- 所有可交互元素尺寸 ≥44px
- 设计师确认信息层级无误

---

### S3 — 规范校验（强制门槛）

**目标**：线框稿进入高保真前，强制校验是否符合设计规范。**不通过不得进入 S4**。

**AI 自动校验项**：


| 校验项    | 标准                                                       | 容忍度              |
| ------ | -------------------------------------------------------- | ---------------- |
| 色彩     | 全部使用 `design/USDD-component-guidelines.md` 中的 token，零裸色值 | **100%**         |
| 字体     | 字阶（Heading/Body/Label/Caption）符合规范定义                     | **100%**         |
| 圆角     | 按钮/卡片/弹窗分别使用规范定义的 token                                  | **100%**         |
| 间距     | margin/padding 符合 4px 基准网格                               | **≥95%**         |
| 触控尺寸   | 可交互元素 ≥44px                                              | **≥95%**         |
| **总分** | 加权总分                                                     | **≥95% 方可进入 S4** |


**处理规则**：

- 不通过项必须**一次性全部修复**后重新校验
- 不允许带着不合规项进入 S4
- 校验结果输出为一段简短的通过/不通过声明（不需要单独保存文件）

**Prompt 模版**：

**校验 — 固定校验 Prompt（存为团队快捷模板）**

```md
请对以下文件进行 USDD 设计规范校验：
[文件路径 或 粘贴代码]

对照 `design/USDD-component-guidelines.md`，逐项检查：

【色彩】
- 是否存在裸色值（非 CSS Token）？
- 是否出现了规范外的颜色？

【字体】
- 字号是否全部来自字阶规范（10 / 11 / 12 / 14 / 16 / 20 / 32px）？
- 字重是否符合规范定义（Heading / Body / Label / Caption）？

【圆角】
- 按钮是否使用规范定义的 token？
- 卡片是否使用规范定义的 token？
- 弹窗 / 抽屉是否使用规范定义的 token？

【间距】
- margin / padding 是否符合 4px 基准网格？
- 卡片内边距、列表间距是否符合规范？

【触控】
- 所有可交互元素高度是否 ≥ 44px？

【层级】
- z-index 层级关系是否符合规范（遮罩 < 抽屉 < 弹窗）？

输出格式：
## 校验报告
总体评分：[通过项数]/[总项数]
### ❌ 不通过项
[序号] [问题描述] · 位置：[CSS 类名或行号] · 修复建议：[具体修改]
### ✅ 通过项
[列表]
### 结论：通过，可进入 S4 / 不通过，需修复后重新校验

限制：
- 不修改页面布局结构
- 不讨论主观审美
- 只按项目规范校验，不引用外部风格偏好覆盖项目规范
```

**修复 — 批量修复 Prompt**

```md
请根据校验报告，一次性修复所有 ❌ 项，
修复时不改动任何未标记问题的代码，
修复完成后再次运行校验确认全部通过。
```

### S4 — UI 设计稿

**目标**：在校验通过的线框稿基础上，套用完整设计规范，生成高保真 HTML 设计稿。

**AI 协作步骤**：

1. AI 读取：线框稿 + `design/USDD-component-guidelines.md` + `USDD2.0/design.md` + `USDD2.0/figma-design-index.md`
2. AI 套用品牌色、字体、图标、组件规范，生成高保真 HTML
3. 设计师审批关键参数：主视觉、层次关系、图标选用、关键文案排版

**关键检查项**：

- 色差 deltaE < 2（品牌色精度）
- 图标线宽统一（参考 `design/USDD-asset-inventory.md`）
- 弹窗/Toast/空态等组件状态齐全

**Prompt 模版**：

**A — 主 UI 生成 Prompt**

```md
请基于以下线框稿，生成符合 USDD 设计规范的高保真 UI 设计稿：

线框稿路径：[线框稿文件路径]
设计规范路径：`design/USDD-component-guidelines.md`

生成要求：
1. 完整应用所有 CSS Token（在 :root 声明）
2. 严格使用规范内的颜色、字体、圆角、阴影、间距和组件
3. 补齐所有关键状态：
   - 默认态
   - hover / active / disabled（如适用）
   - 空态 / 加载 / 错误
4. 保留线框稿的所有交互 JS 逻辑
5. 新增：按钮 hover / active 交互反馈
6. 每个屏幕下方保留设计注释（更新为 UI 层面的说明）
7. 输出文件：`ui-{功能名}-v1.html`

限制：
- 不使用裸色值
- 不擅自新增风格化元素
- Skill 与项目规范冲突时，以 `design/USDD-component-guidelines.md` 为准
```

**B — 按模块迭代（大型页面推荐）**

> 不要一次生成所有页面。按模块迭代，每次只处理 2–3 个组件，保证质量。

```md
当前任务：只处理「[页面名]」的以下区域：
- [组件1]（CSS 类名：.[class-name]）
- [组件2]（CSS 类名：.[class-name]）

其他区域保持与线框稿相同，不要改动。
```

**C — 规范外新组件处理**

```md
我需要一个「[组件名]」组件，设计规范中没有现成定义。
请基于以下约束设计并实现：
- 必须用规范内的 Token（不新增颜色）
- 圆角遵循现有层级（参照 `design/USDD-component-guidelines.md`）
- 给出 2 个方案，我来选择
- 选定后将样式补充到注释中，便于后续提取为规范
```

**推荐 Claude Skills**（在 Prompt 中显式声明）：


| Skill                   | 用途                        |
| ----------------------- | ------------------------- |
| `UI-UX-Pro-Max`         | UX 规则库 + 智能搜索，减少「AI 味」    |
| `frontend-design`       | 精致排版，消除生硬感                |
| `web-design-guidelines` | 间距/栅格/排版规范                |
| `web-accessibility`     | WCAG 2.1 合规，aria 标签，对比度验证 |


> Skill 与 `design.md` 冲突时，**以项目规范 `design.md` 为准**。

**产出**：`iterations/v{x.y.z}/ui-{功能名}-v{N}.html`

### S5 — 走查修改

**目标**：设计师量化走查，AI 精确执行修改，最多 3 轮收敛。

**走查反馈格式**（必须使用标准表格）：


| ID   | 页面  | 问题描述               | 期望效果            | 优先级 |
| ---- | --- | ------------------ | --------------- | --- |
| W-01 | 首页  | 主按钮高度 40px，应为 48px | 改为 height: 48px | P0  |
| W-02 | 弹窗  | 标题字号 16px，应为 18px  | font-size: 18px | P1  |


**规则**：

- 不接受「感觉不对」「整体偏小」等模糊反馈
- 每处修改 AI 必须标注对应走查 ID（如：`// fix W-01`）
- 走查最多 **3 轮**；超过 3 轮说明 S1 简报不清晰，需回退补充 `brief-{功能名}.md`

**优先级处理**：

- 🔴 P0（品牌色错误、功能缺失、文案错误）：当轮必修
- 🟡 P1（间距偏差 >4px、字号错误、图标缺失）：当轮完成，修复率 ≥80%
- 🟢 P2（微调级偏差 1-2px）：可在 S6 前处理或下版本

**Prompt 模版**：

**准备 — 走查会前：让 AI 生成走查清单**

```md
请为以下设计稿生成走查清单，格式为可勾选的 Markdown 表格：
[设计稿路径]

按以下维度组织：
1. 视觉还原度（与 Figma 对比）
2. 交互完整性
3. 文案准确性
4. 边界状态覆盖（空态 / 加载 / 错误）
5. 无障碍（色彩对比度、触控尺寸）
```

**记录 — 走查反馈标准格式（直接用这个模板）**

```md
## 走查反馈 · [功能名] · [日期]

| ID   | 页面      | 问题描述                             | 期望效果                        | 优先级 |
|------|-----------|--------------------------------------|-------------------------------|--------|
| W-01 | 首页      | 主按钮高度 40px，应为 48px           | 改为 height: 48px             | P0     |
| W-02 | 弹窗      | 标题字号 16px，应为 18px             | font-size: 18px               | P1     |
| W-03 | 列表      | 列表间距 6px，视觉上太紧             | 改为 gap: 8px                 | P2     |
```

**执行 — 将反馈交给 AI 执行修改**

```md
请根据以下走查反馈，修改设计稿 [文件路径]：

[粘贴走查反馈表格]

修改规则：
- 只修改表格中列出的问题，其余不动
- P0 / P1 优先处理，P2 在 P1 全部完成后处理
- 每处修改在代码注释中标注走查 ID（如：`/* 走查 W-01 */`）
- 修改完成后列出变更摘要

限制：
- 不接受模糊反馈自行发挥
- 不新增未在走查表中要求的改动
- 若累计超过 3 轮，提醒回退补充 `brief-{功能名}.md`
```

**产出**：`iterations/v{x.y.z}/walkthrough-{功能名}-{日期}.md`

### S6 — 交付包

**目标**：生成开发可直接使用的完整交付物，无需开发反复询问设计师。

**AI 从 HTML 代码中自动提取并生成**：

- Markdown 标注文档（CSS Token 名称、组件尺寸、动画参数）
- 可复用 `components.css`（含 CSS 变量定义）
- 切图清单（图标名称 + 尺寸 + SVG 来源）

**Prompt 模版**：

**A — 生成标注文档**

```md
请读取 [终版 UI 文件路径]，生成开发交付标注文档。

输出格式为 Markdown，包含：

## 交付文档 · [功能名] · [版本] · [日期]

### 页面清单
[每个屏幕名称 + 触发条件]

### 全局样式
- 字体栈 / CSS Token 声明（完整 :root）/ 页面背景色

### 各页面组件标注
#### [页面名]
| 组件 | 尺寸 | 背景 | 字体规格 | 圆角 | 交互 |
|------|------|------|---------|------|------|

### 动画参数
[所有 transition 和 animation 规格]

### 异常状态说明
[空态 / 加载态 / 错误态的触发条件和 UI 变化]

### 开发注意事项
[容易出错的地方，最多 10 条]

限制：
- 不写模糊描述，如”适中””大约”
- 所有尺寸和样式参数必须来自代码或规范
- 若发现缺失状态页或缺失资产，明确列为待补项
```

**B — 生成切图需求清单**

```md
请从 [终版 UI 文件路径] 中识别所有需要切图的资源：
- 无法用 CSS 实现的图标
- Token 图标（需要 PNG / SVG）
- 插图、背景图

输出格式：
| 资源名 | 尺寸 | 格式 | 用途 | 所在页面 |
|--------|------|------|------|---------|
```

**C — 提取可复用 CSS 组件**

```md
请从终版文件中提取所有可独立复用的 CSS 组件，
生成 components.css 文件，要求：
- 每个组件有注释说明：组件名、用途、使用示例
- 按 `design/USDD-component-guidelines.md` 中的组件顺序排列
- 不包含页面特定的样式，只保留通用部分
```

**设计师需手动补充**：

- Figma 设计稿链接（记录到 `USDD2.0/figma-design-index.md` 或 `iterations/v{x.y.z}/figma-mapping.md`）
- 特殊动效参数说明（如有）

**Figma → 代码工作流**：

> 设计师完成 Figma 交付后，开发可通过 **Figma MCP** 让 Claude Code 直接读取 Figma 设计稿的布局、组件、Token 和样式，自动生成高还原度前端代码（HTML/CSS/React），大幅减少手工还原偏差和反复走查成本。

**交付包完整性检查**：

- 终版 HTML 设计稿（所有状态页面）
- Figma 链接已记录到索引
- Markdown 标注文档（含 Token 映射）
- 切图清单（图标路径 + 尺寸）
- `components.css`（可复用样式变量）

**产出**：

- `iterations/v{x.y.z}/annotation-{功能名}.md`
- `iterations/v{x.y.z}/components.css`
- `USDD2.0/figma-design-index.md`（更新）

### S7 — 开发验收

**目标**：上线前通过截图对比验证 UI 还原度 ≥90%，设计师签字放行。

**AI 协作步骤**：

1. AI 截图对比（设计稿 vs 开发实现）
2. AI 输出差异报告（逐项标注：设计稿值 vs 实现值）

**Prompt 模版**：

**A — 截图对比验收 Prompt**

```md
我有开发实现截图（已上传），请对照标注文档 [文件路径]，
列出所有视觉差异：

输出格式：
| ID | 差异位置 | 设计稿值 | 开发实现值 | 严重程度 | 修复建议 |
|----|---------|---------|-----------|---------|---------|
[P0 = 严重偏差，P1 = 明显差异，P2 = 细节优化]

最后给出整体还原度评分（0–100%），并判断是否可签字放行。

限制：
- 不只写”有偏差”，必须写出具体数值或具体表现
- 不把主观审美偏好当成缺陷
- 未达到上线标准（还原度 <90%）时必须明确写出”不可放行”
```

**B — 生成修复建议单（给开发）**

```md
基于上面的差异清单，生成给开发工程师的修复说明：
- P0 问题：本轮必须修复，不得上线
- P1 问题：修复率 ≥ 80% 后可上线，剩余进入下个版本
- P2 问题：积累后统一处理，不阻塞发版

每条修复说明包含：具体修改的 CSS 属性和值，
让开发不需要再询问设计师。
```

**验收严重程度**：


| 严重程度 | 标准                  | 处理方式          |
| ---- | ------------------- | ------------- |
| P0   | 品牌色错误、文案错误、功能缺失     | 打回本轮修复，不得上线   |
| P1   | 间距偏差 >4px、字号错误、图标缺失 | 修复率 ≥80% 后可上线 |
| P2   | 微调级偏差（1–2px）        | 可下版本处理        |


**验收通过标准**：整体还原度 ≥90%，**设计师签字**。

**产出**：`iterations/v{x.y.z}/acceptance-{功能名}-{日期}.md`

## 四、交付物标准


| 交付物    | 格式                 | 命名规范                        | 示例                            |
| ------ | ------------------ | --------------------------- | ----------------------------- |
| 设计简报   | `.md`              | `brief-{功能名}.md`            | `brief-psm-redesign.md`       |
| UI 设计稿 | `.html` + Figma 链接 | `ui-{功能名}-v{N}.html`        | `ui-vault-mint-v2.html`       |

## 五、AI 使用规范

### 可用 Skills


| Skill                | 用途                  | 触发示例                  |
| -------------------- | ------------------- | --------------------- |
| `prototype-generate` | 生成 HTML 线框或高保真原型    | "帮我生成 PSM 功能的线框稿"     |
| `prd-review-ux`      | UX 视角审查 PRD 或设计稿    | "请从 UX 角度评审这个设计简报"    |
| `prd-review-all`     | 全角色并行预评审            | "请对这个设计方案做全角色评审"      |
| `baseline-merge`     | 版本上线后合并设计基线         | "帮我将 v2.1.0 的设计合并到基线" |
| `sync-drive`         | 同步交付包到 Google Drive | "帮我同步设计交付包到 Drive"    |


### 设计知识库读取顺序

AI 每次设计对话应读取（按优先级）：

1. `design/USDD-component-guidelines.md` — Token、组件规范
2. `USDD2.0/design.md` — 端级设计约束
3. `USDD2.0/figma-design-index.md` — 现有设计稿索引
4. 相关基线 PRD（`USDD2.0/modules/`）— 了解现有功能状态
5. 迭代版本 PRD（`USDD2.0/iterations/v{x.y.z}/prd-{name}.md`）— 当前需求

### AI 不适用场景


| 场景          | 原因                            |
| ----------- | ----------------------------- |
| **品牌创意发散**  | 早期头脑风暴阶段，AI 倾向给出「正确但平庸」的方案    |
| **用户情感判断**  | AI 无法感知用户操作时的情绪和压力            |
| **设计优先级博弈** | 跨职能设计范围争议需要人工决策               |
| **无障碍专项合规** | 法律层面的 A11y 合规需要专业审计，AI 只做初步检查 |

## 六、PM 原型 vs 设计师 Figma 定位


| 维度   | PM 的 HTML 原型                        | 设计师的 Figma                           |
| ---- | ----------------------------------- | ------------------------------------ |
| 定位   | 意图表达（80% 精度）                        | 设计决策（100% 精度）                        |
| 用途   | 评审沟通、需求对齐                           | 开发实现、视觉交付                            |
| 开发衔接 | 参考用，不直接转代码                          | 通过 Figma MCP + Claude Code 生成高还原前端代码 |
| 关系   | 互补不替代 — PM 原型定义「做什么」，Figma 定义「长什么样」 |                                      |

## 七、质量门禁

### S3 规范校验门槛（进入 S4 前必过）

- 色彩 Token 100%（零裸色值）
- 字体字阶 100%（无自定义字号）
- 圆角 Token 100%（按钮/卡片/弹窗分别符合规范）
- 间距 ≥95% 符合 4px 网格
- 可交互元素触控尺寸 ≥44px

### S6 交付包完整性门槛（交付开发前必过）

- 终版 HTML 包含所有状态（正常/空/加载/错误）
- Figma 链接已记录到 `figma-design-index.md`
- 标注文档包含所有 Token 映射和组件尺寸
- 切图清单完整（每个图标有路径和尺寸）
- `components.css` 可直接被开发引用

### S7 开发验收门槛（上线前必过）

- 整体还原度 ≥90%
- P0 问题全部解决
- P1 问题修复率 ≥80%
- 设计师签字

## 八、避坑指南


| 陷阱               | 表现                      | 规避方法                                |
| ---------------- | ----------------------- | ----------------------------------- |
| **跳过 S3 直接做 S4** | 高保真稿里充满裸色值和不规范字号，返工成本高  | S3 是硬门槛，不通过不进入 S4                   |
| **走查用感性描述**      | AI 按模糊描述修改方向不一致，越改越乱    | 走查表格必须量化：数值 + 页面 + 期望值              |
| **走查超过 3 轮**     | 设计简报不清晰，需求在走查阶段才浮现      | 超 3 轮时停止，回退补充 `brief-{功能名}.md`      |
| **AI 用裸色值**      | 原型色彩与规范 Token 脱节，开发无法复用 | 每次对话显式告知 AI 读取 component-guidelines |
| **Figma 链接不记录**  | 开发找不到设计稿，反复向设计师询问       | S6 完成时立即更新 `figma-design-index.md`  |
| **Skill 安装未声明**  | Skill 已安装但 AI 未按规范执行    | Prompt 中必须显式声明使用的 Skill             |
| **脱离 PM 主流程并行**  | 设计稿基于过时 PRD，与最终需求不一致    | 与 PM 确认 PRD 定稿版本后再进入 S2             |
