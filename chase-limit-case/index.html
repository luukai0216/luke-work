这份案例想证明什么

能读懂业务约束，能把规则组织成清晰的手机界面，也能处理部分成交、终止、撤单和连接异常。以下区分「官方事实」「方案假设」「待验证项」，不将推测或预期收益包装成已经发生的结果。页面为独立设计探索，尚未核验 KuCoin 当前 APP 组件规范。

01 / FRAME THE PROBLEM

用户交给系统的，
是一段持续执行的交易意图。

目标用户：熟悉普通限价交易，希望减少盯盘与反复改价的人。用户需求假设来自题目与规则分析，尚未开展访谈。

01

我要怎么追？

用户不再输入固定委托价，而是选择价格跟随规则。默认跟随本方最优盘口，并解释买入与卖出的区别。

02

最多追到哪里？

仅显示一个百分比，难以形成价格直觉。将抽象距离换算成具体停止线，紧邻下单决策。

03

现在到底怎么样？

部分成交不意味着运行结束。将「运行状态」和「成交进度」一起展示，结束时说明剩余数量的去向。

设计目标：用户能用自己的话复述“跟随谁、何时停、剩余怎么办”。不以“保证成交”“最优成交价”作为产品承诺。只挂单约束也意味着可能持续等待或提交被拒绝。

决策 01 / 信息分层

主表单给摘要，面板解释规则。

盘口与下单操作保留在同一上下文；详细设置在底部面板展开，保存后回填可读摘要。

取舍：增加一次设置操作，换取主表单可扫描性；停止线必须直接露出，不能只藏在面板里。

决策 02 / 价格语义

明确区分停止线与成交价格。

「预计停止线」描述终止条件；「当前委托价」描述挂单；「成交均价」描述已成交结果。

取舍：多展示一行解释，避免用户把停止线误认为必然成交价或止损线。

决策 03 / 订单组织

一个追逐任务，一张委托卡片。

价格更新不生成新的列表卡片。运行状态、当前委托价和累计成交数量保持在固定位置。

取舍：改价过程放进详情，默认列表优先回答“还在追吗、成交多少”。

决策 04 / 产品范围

先完成默认规则下的闭环。

本次不扩展启动条件、自定义更新频率、偏移追价和自动转市价。开多为主路径，开空提供方向对照。

取舍：降低首次配置负担。平仓沿用只减仓约束，需补足仓位不足状态后再进入完整上线范围。

03 / MAKE THE RULES EXPLICIT

先约定规则，再画页面。

以下为本次作业的统一规则假设，不是 KuCoin 已上线产品规范。示例只用于理解与演示，不构成参数建议。

  1. 跟随本方盘口
    买入跟买一，卖出跟卖一；仅调整未成交数量。每次以只挂单方式提交，不保证成交。
  2. 初始基准固定
    创建时锁定初始本方盘口 P₀。买入停止线 P₀×(1+d)，卖出停止线 P₀×(1−d)。主路径只支持百分比 d。
  3. 朝不利方向触线即终止
    买一 ≥ 买入停止线，或卖一 ≤ 卖出停止线，停止改价并请求撤销剩余。未触线时跟随盘口，基准不随行情滚动。
  4. 预览与实际区分
    提交前显示预计值；确认时基准发生变化则刷新摘要并再次确认；创建后展示服务端返回的实际基准与停止线。
  5. 结束以服务端确认结果为准
    触线或手动撤单先进入处理中；撤销确认前可能继续成交。已成交部分不会因撤单而消失，也不会被自动平仓。
  6. 需要与产品／研发确认
    价格精度与取整、最大距离范围、最小数量、改价频率、只挂单拒绝重试和保证金检查。原型演示阈值不代表正式交易所限制。

复杂度，藏在中间状态里。

06 / UI THAT SERVES THE TASK

用视觉秩序降低理解成本。

这些是方案采用的 UI 原则；正式提交前，需与实际 KuCoin APP 的字体、间距、颜色偏好和组件行为对齐。

稳定的信息骨架

价格与数量使用等宽数字特性；字段位置不随行情变化移动。状态、进度、价格、边界、操作保持固定阅读顺序。

有含义的颜色

绿色用于买入及主操作，卖出使用对应方向色。警示色提示终止原因；所有状态同时提供文字，不依赖颜色判断。

为手机输入设计

输入单位固定显示、数字键盘、就地报错；主要按钮至少 44px 高。面板可滚动，软键盘、长文案与系统大字体需真机走查。

优化对照应是“信息表达前后”，不能虚构 KuCoin 原版缺陷。例如：仅展示「0.5%」→ 同时展示「预计停止线 60,300 USDT」；仅展示「部分成交」→「追逐中＋已成交 20%」。后续拿到真实截图，再讨论实际界面的改版机会。
07 / PROVE IT, THEN PRESENT IT

让每个设计判断，
都能接受检验。

尚未开展用户测试，不填写虚构转化率或满意度。下面是可执行的验证计划与最终交付顺序。

小规模可用性验证

  1. 任务 01
    设置有边界的买入追逐单

    观察用户能否找到入口、设置数量与边界，并解释触线后会发生什么。记录用时、误填及求助点。

  2. 任务 02
    解释部分成交订单

    展示已成交 0.02 / 0.10 BTC。请用户说出剩余量是否还在运行，以及“当前委托价”和“成交均价”的区别。

  3. 任务 03
    撤销剩余并解释结果

    检查用户是否误以为撤单会取消已成交交易或自动平仓，再验证终止文案能否纠正理解。

建议招募 5 位有合约限价单经验的用户，做定性测试。将“关键规则理解正确”作为优先观察项；小样本结果不外推为上线业务提升。

建议完成顺序

  1. 第 1 步
    补真实 APP 调研

    记录 KuCoin、OKX、Gate 的版本与截图，标注入口、字段顺序、帮助方式及状态处理。无需真实下单验证。

  2. 第 2 步
    冻结规则与状态表

    确认参考价、距离基准、触线方向、剩余数量处理和只挂单拒绝策略；在 Figma 中复用同一套文案。

  3. 第 3 步
    把这版原型打磨为设计稿

    建立输入框、订单卡片、状态标签和底部面板组件；补齐空值、错误、加载、键盘和大字体场景。

  4. 第 4 步
    测试、修改，再讲述

    留下至少一条“发现问题→修改→再次验证”的真实记录。它比增加装饰性页面更有说服力。

08 / INTERVIEW NARRATIVE

用 8 分钟，讲清你的判断。

不要逐屏介绍按钮。围绕“为什么难、如何取舍、如何证明”展开，让页面成为论据。

  1. 00–01′
    定义问题

    用户把手动改价交给系统，新的难点是理解规则与感知执行，而不仅是多一个订单类型。

  2. 01–03′
    展示依据与取舍

    说明竞品事实、方案假设和暂未确定项。解释为什么默认跟随本方一价，为什么边界需要换算成价格。

  3. 03–06′
    演示一笔完整订单

    设置 0.10 BTC → 确认 → 部分成交 → 触线终止 → 查详情。用数量与价格的一致性证明理解。

  4. 06–08′
    解释异常与验证

    展示撤单中可能成交、断网不等于停止，以及测试中你计划检查的误解。区分已完成与待验证工作。

准备好回答这些追问

为什么不直接让用户输入最高买价？

这是值得测试的替代方案。百分比跨币种更容易复用，但理解成本更高；直接输入价格更直观，却需要随价格尺度重新判断。本版保留竞品距离概念，并提供价格换算；可以通过两种表达的理解测试再决定默认方式。

为什么停止线不藏在高级设置里？

它决定用户接受的追价范围，是核心决策。详细说明可以渐进展开，但当前边界与触线后果必须在下单前可见。

为什么不显示每一次撤单重挂？

用户关注的是同一笔交易意图的进度。把内部改价过程全部铺在列表会稀释关键信息；细节放入订单过程记录即可。

你的设计真的提高效率了吗？

目前是待验证的设计假设。我会比较规则理解、任务完成、误操作和求助情况；只有取得数据后，才讨论提升幅度。

如何兼顾高频交易用户？

优先保留交易页上下文与设置摘要；验证后可评估记忆上次配置和确认偏好，但不能静默复用跨交易对的价格边界。首次使用与高频使用可以有不同的信息展开程度。

“我把自动追价设计成一段可理解的过程：
先说明规则，再呈现进度，最后解释结果。”
