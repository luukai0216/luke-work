## P0 紧急｜颜色对比度大面积失败

### 问题背景

v6 审计对 USDD 全站文字元素做了对比度测试，结论：

- **WCAG AA 合规率：仅 21%**
- **不合规率：79%**
- 生态对比：TronScan 86% · TRON-Web 67% · JustLend Portal 64% · **USDD 21%（垫底）**

```
生态 WCAG AA 合规率横向对比：

TronScan      ████████████████████████████ 86%
TRON-Web      ██████████████████████ 67%
JustLend      ████████████████████ 64%
USDD          ██████ 21% 🚨
```

### 根本原因：5 档半透明白色文字体系

USDD 设计规范用透明度来区分文字层级，这套体系在深色背景以外的场景严重失效：

| 文字档位 | 颜色值 | 对比度（深色背景）| AA 要求 | 结论 |
|---------|-------|:-----------------:|:------:|:---:|
| text-primary | `rgba(255,255,255,1.0)` | 21:1 | 4.5:1 | ✅ 通过 AAA |
| text-80 | `rgba(255,255,255,0.8)` | ~15:1 | 4.5:1 | ✅ 通过 AA |
| text-60 | `rgba(255,255,255,0.6)` | ~7:1 | 4.5:1 | ⚠️ 通过，但有背景依赖风险 |
| **text-40** | **`rgba(255,255,255,0.4)`** | **~4.0:1** | 4.5:1 | **❌ FAIL（差一点点）** |
| **text-20** | **`rgba(255,255,255,0.2)`** | **~1.9:1** | 4.5:1 | **❌ FAIL（严重不合规）** |

text-40 和 text-20 被大量用于次要文字、辅助说明、placeholder 等元素，这解释了为什么 79% 的文字元素都不过关。

### 合规风险说明

这不是"体验优化"的问题，而是真实的**法律合规风险**：

- **欧盟 EAA（European Accessibility Act）2025 已正式生效**，要求数字金融产品满足 WCAG AA
- **美国 ADA（Americans with Disabilities Act）** 已有多起针对金融类网站的诉讼案例
- 稳定币 / DeFi 产品在面向欧美用户时，WCAG 合规是法律底线，不达标存在被监管或诉讼的风险

### 整改方案

---

#### 方案 A（推荐）｜废弃透明度体系，改用固定色值 + 字重区分层级

**核心思路：** 不再靠"越来越透明"来表达次要感，改用"越来越灰的固定颜色"加上字重轻重来区分主次。颜色不透明，就不会受背景影响。

```
现有（依赖透明度，有合规风险）：
text-primary  rgba(255,255,255,1.0)   21:1  ✅
text-80       rgba(255,255,255,0.8)  ~15:1  ✅
text-60       rgba(255,255,255,0.6)   ~7:1  ⚠️
text-40       rgba(255,255,255,0.4)   ~4:1  ❌
text-20       rgba(255,255,255,0.2)  ~1.9:1 ❌

建议替换为（固定色 + 字重，与背景无关）：
主要文字   #FFFFFF  SemiBold 600  对比度 21:1  ✅
次要文字   #B0B8C1  Regular  400  对比度 ~7:1  ✅
辅助文字   #7A8490  Regular  400  对比度 ~4.8:1 ✅
禁用文字   #5A6475  Regular  400  对比度 ~4.6:1 ✅
```

**在 Figma 里怎么做：**
1. 在 Color Variables 里新建 4 个文字颜色 Token，命名为 `text/primary`、`text/secondary`、`text/tertiary`、`text/disabled`
2. 把现有 text-40、text-20 的 Token 逐一替换为新的固定色值
3. 更新所有用到这两个档位的组件（次要说明文字、placeholder、辅助标签、禁用状态）

| 优点 | 缺点 |
|------|------|
| 从根源解决，任何背景下都合规 | 工作量最大，Figma 组件全量更新 |
| 跨页面、跨场景稳定 | 视觉语言有变化，半透明质感会消失 |
| 一劳永逸，后续不会反复踩坑 | 需要前端配合全量替换 CSS 变量 |

> **Owner：** USDD 设计 + 前端
> **工作量：** 设计约 2–3 天（Token 重定义 + Figma 组件更新）+ 前端约 1–2 天（CSS 变量替换）

---

#### 方案 B｜最小改动：只把透明度提高到安全阈值

**核心思路：** 不改设计语言，只把不合规的 text-40 和 text-20 的透明度数值往上调，让它勉强通过 AA 标准。

```
当前（不合规）：
text-40  rgba(255,255,255,0.40)  对比度 ~4.0:1  ❌
text-20  rgba(255,255,255,0.20)  对比度 ~1.9:1  ❌

调整后（刚好合规）：
text-40  rgba(255,255,255,0.62)  对比度 ~4.6:1  ✅（仅在深色背景下）
text-20  rgba(255,255,255,0.50)  对比度 ~5.0:1  ✅（仅在深色背景下）
```

**在 Figma 里怎么做：**
1. 找到 text-40 和 text-20 两个 Color Variable
2. 将透明度（Alpha）分别改为 62% 和 50%
3. 不需要改任何组件，Token 自动更新全站

| 优点 | 缺点 |
|------|------|
| 改动极小，Figma 只需改 2 个数值 | 仍然依赖背景色——如果页面出现浅色区块，依然会失败 |
| 视觉几乎没有变化 | 只是"刚好通过"，没有安全余量 |
| 前端同步修改 CSS 变量即可完成 | 长期有反复不合规的风险 |

> **Owner：** 设计改 Figma Token，前端改 CSS 变量
> **工作量：** 设计约 0.5 天 + 前端约 0.5 天

---

#### 方案 C｜只修复问题档位，高档位保持不变

**核心思路：** text-primary、text-80、text-60 本来就合规，保持不动。只把 text-40 和 text-20 这两个问题档位换成不透明的固定色，其余不变。设计语言上形成"高档位半透明、低档位实色"的混合结构。

```
保持不变：
text-primary  rgba(255,255,255,1.0)  ✅  保持
text-80       rgba(255,255,255,0.8)  ✅  保持
text-60       rgba(255,255,255,0.6)  ⚠️  保持（仅限深色背景场景）

替换：
text-40  → #8A95A3（不透明中灰，对比度 ~5.2:1）✅
text-20  → 废弃，视情况合并到 text-40 或 text/disabled 档位
```

**在 Figma 里怎么做：**
1. 将 text-40 的颜色从 `rgba(255,255,255,0.4)` 改为 `#8A95A3`（或接近的不透明灰）
2. 搜索 Figma 中所有使用 text-20 的图层，根据上下文改为 text-40 或 disabled 状态

| 优点 | 缺点 |
|------|------|
| 改动范围比方案 A 小 | 上下档位视觉语言不统一（一些半透明一些实色）|
| 解决了最主要的不合规问题 | text-60 保留了背景依赖风险 |
| 保留了高档位的品牌半透明质感 | 设计规范文档需要明确写清楚"哪个档位能在哪里用" |

> **Owner：** 设计改 Figma，前端配合
> **工作量：** 设计约 1 天 + 前端约 0.5 天

---

#### 方案 D｜场景锁定：规定 text-40 / text-20 只允许用在深色背景上

**核心思路：** 不改颜色值本身，改的是"使用规则"。在设计规范中明确写死：text-40 和 text-20 只允许出现在背景深度 ≥ 某个阈值（如 `#0A1520` 以下）的深色场景，严禁在卡片、弹窗、浅色模块里使用。

**在 Figma 里怎么做：**
1. 在 Color Variables 的 Description 字段里标注使用限制（如"仅限深色背景，禁止用于 Modal、卡片白底"）
2. 在 Design System 文档页里加入"禁止/允许"的对比示例
3. 前端可配合用 CSS 变量命名加提示，或 Stylelint 规则拦截

| 优点 | 缺点 |
|------|------|
| 不改任何色值，外观完全不变 | 依赖团队执行纪律，有人不看规范就会踩坑 |
| 工作量极小 | 没有技术手段自动拦截错误使用 |
| — | 如果页面未来出现浅色模块，问题会卷土重来 |
| — | 本质上没有"解决"问题，只是"限制了使用范围" |

> **Owner：** 设计（更新规范文档）+ 前端（可选 Stylelint 规则）
> **工作量：** 约 0.5 天（规范文档更新）

---

#### 方案 E｜渐进替换：按页面模块分批修复

**核心思路：** 如果全量替换风险太高，可以按模块优先级拆开来做。先把用户最常看到的核心模块（首屏 Hero、数据面板、CTA 区域）改成合规颜色，其余模块排后续迭代。

**分批顺序建议：**

| 批次 | 范围 | 优先原因 |
|------|------|---------|
| 第 1 批（立即）| 首屏 Hero 文字、主要数据展示（APY、TVL 等）| 曝光量最大，用户最先看到 |
| 第 2 批（1–2 周内）| 功能说明文字、表格辅助列、Tooltip | 使用频率高 |
| 第 3 批（下个迭代）| 页脚辅助信息、placeholder、禁用状态 | 相对次要 |

**在 Figma 里怎么做：**
1. 第 1 批：在设计稿里找到 Hero 区域所有使用 text-40 / text-20 的图层，改为方案 A 的固定色
2. 依次推进后续批次，每批交付前用对比度检查工具（Figma Contrast Checker 插件）验证

| 优点 | 缺点 |
|------|------|
| 风险可控，分批上线 | 过渡期内全站颜色不统一 |
| 可以先快速拿到最大曝光区域的合规率提升 | 整体周期拉长 |
| 每批都可以单独评估效果 | 需要维护"旧 Token + 新 Token"两套 |

> **Owner：** 设计 + 前端按批次交付
> **工作量：** 第 1 批约 1 天，全量完成约 3–4 天

---

### 方案对比总结

| 方案 | 改动幅度 | 合规稳定性 | 视觉变化 | 工作量 | 推荐场景 |
|------|:-------:|:---------:|:-------:|:-----:|---------|
| A · 全面改固定色 | 大 | ⭐⭐⭐ 最稳 | 半透明质感消失 | 3–5 天 | 长期解决，有设计资源时首选 |
| B · 调高透明度 | 极小 | ⭐ 有背景依赖 | 几乎无变化 | 1 天内 | 紧急临时修复，后续再做 A |
| C · 只修复问题档位 | 小 | ⭐⭐ 较稳 | 低档位有轻微变化 | 1–2 天 | 折中方案，平衡速度和质量 |
| D · 限制使用场景 | 极小 | ⭐ 依赖人工执行 | 无变化 | 0.5 天 | 仅作临时规范补丁，不建议单独用 |
| E · 分批渐进 | 中 | ⭐⭐⭐ 最终同 A | 分批过渡 | 3–4 天 | 风险敏感项目，需分批上线时 |

## v6 审计的核心判断

> **"USDD 无障碍灾难：79% 文字元素对比度未达 WCAG AA。根因是规范中定义的 5 档半透明文字体系——`rgba(255,255,255,0.4)` 对比度仅 4.0，`rgba(255,255,255,0.2)` 对比度 1.9 完全不合规。这是真实的用户流失 + 潜在合规风险。"**
>
> — UI规范落地审计 v6，WCAG 无障碍对比度章节
