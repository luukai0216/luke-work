# 知识库协作规则

> 本文件定义知识库的写作规范、协作流程、维护规则、AI 交互规则。所有参与者须遵守。

---

## 一、写作规范

### 1.1 文档视角

| 规则 | 说明 |
|------|------|
| 产品视角 | 用自然语言描述用户流程和业务逻辑，不涉及代码实现 |
| 面向多角色 | QA 能据此写用例，Dev 能理解业务逻辑，设计师能核对交互 |
| 源码索引折叠 | 如需关联代码路径，放在 `<details>` 标签内，默认不展开 |

### 1.2 语言与术语

| 规则 | 说明 |
|------|------|
| 中文为主 | 正文使用中文 |
| 英文保留 | 代码标识符、API 名称、技术术语保留英文原文 |
| 术语统一 | 使用 `shared/glossary.md` 中的定义，不自造缩写 |
| 首次出现注释 | 术语首次出现时标注英文，如：质押（Stake） |

### 1.3 格式规范

| 元素 | 格式 |
|------|------|
| 用户流程 | 编号步骤（1. 用户点击 → 2. 系统展示 → ...） |
| 业务规则 | BR-xxx 编号（BR-001: 转账金额不得超过可用余额） |
| 异常场景 | 表格（场景 / 触发条件 / 系统行为 / UI 表现） |
| UI 文案 | 中英文都要提供，写在「UI 文案规格」章节 |
| 不确定项 | 标注「⚠️ 待确认」，附上不确定的原因 |
| 图片引用 | 使用相对路径，格式 `![描述](../prototype/screenshots/xx.png)` |

### 1.4 文件命名规范

| 类型 | 命名规则 | 示例 |
|------|---------|------|
| 模块 PRD | 小写英文 + 连字符 | `transfer-receive.md` |
| 版本 PRD | `prd-` 前缀 + 功能名 | `prd-batch-transfer-v2.md` |
| 版本目录 | `v{major}.{minor}.{patch}` | `v4.8.0/` |
| 原型 | `prototype-` 前缀 + 功能名 | `prototype-homepage-v1.html` |
| 截图 | 编号 + 描述 | `07-transfer-step1.png` |

**禁止使用**：`final`、`最新版`、`修改版`、`new`、`(1)`、`copy`

## 二、协作流程

### 2.1 角色职责

| 角色 | 职责 | 操作权限 |
|------|------|---------|
| 知识库 Owner | 基线合并、结构维护、规则制定、健康检查 | 全目录读写 |
| 版本负责 PM | 该版本 iterations/ 下所有文件 | 该版本目录读写 |
| 设计师 | 设计稿交付、走查、设计决策记录 | design/ 读写 + iterations/ 评论 |
| 其他 PM | 查阅、提修改建议 | 只读 + 评论 |
| 开发 / QA | 查阅 PRD、评审反馈 | 只读（Google Drive 查看者） |

### 2.2 版本生命周期

```
规划中 → PRD 评审 → 跨职能评审 → 开发中 → 测试中 → 已发布
```

| 状态 | 触发条件 | PM 操作 |
|------|---------|---------|
| 规划中 | 需求收集完成 | 创建版本目录 + overview.md |
| PRD 评审 | PRD 初稿完成 | 同步到 Drive，组织产品组内评审 |
| 跨职能评审 | 产品评审通过 | 组织设计 → 技术 → QA 评审 |
| 开发中 | 全部评审通过 | PRD 锁定，变更需走变更流程 |
| 测试中 | 开发提测 | 配合 QA 验证 |
| 已发布 | 上线 | 合并基线，标记版本状态 |

### 2.3 需求变更规则

| 阶段 | 变更流程 |
|------|---------|
| PRD 评审前 | PM 直接修改，无需审批 |
| PRD 评审后、开发前 | 修改 PRD + 在 review-notes.md 记录变更原因 |
| 开发中 | 需评估影响范围，与开发/QA 确认后修改，记录变更原因 |
| 测试中 | 仅允许紧急修复，需全员确认 |

### 2.4 同步节点

| 触发事件 | 操作 | 谁来做 |
|---------|------|--------|
| PRD 初稿完成 | 同步到 Drive | 版本负责 PM |
| 每次评审后修改 | 同步到 Drive | 版本负责 PM |
| 设计交付 Figma | 更新 `figma-design-index.md` 或 `iterations/v{x.y.z}/figma-mapping.md` + 同步 | 版本负责 PM |
| 版本上线 | 合并基线 + 同步 | 知识库 Owner |
| 新术语出现 | 更新 glossary.md + 同步 | 任何 PM |

## 三、知识库维护

### 3.1 目录规则

| 规则 | 说明 |
|------|------|
| modules/ 是基线 | 仅在版本上线后更新，不在迭代过程中直接修改 |
| iterations/ 跟版本走 | 每个版本一个目录，内含该版本所有文件 |
| shared/ 谨慎修改 | 影响所有端，修改前确认跨端兼容 |
| templates/ 持续优化 | 根据使用反馈迭代模板内容 |
| 不创建冗余文件 | 能在已有文件中补充的，不单独建文件 |

### 3.2 健康检查（季度）

每季度由知识库 Owner 执行一次（详见 `docs/doc-health-check.md`）：

- [ ] modules/ 基线是否与线上版本一致
- [ ] iterations/ 中已发布版本是否已合并回基线
- [ ] shared/glossary.md 是否覆盖近期新增术语
- [ ] shared/api-reference.md 是否覆盖新接口
- [ ] figma-design-index.md 是否有新交付的 Figma 链接未填
- [ ] 各模块 PRD 中的「⚠️ 待确认」是否有已确认但未更新的

### 3.3 文件不应包含的内容

| 不要放 | 原因 | 替代方案 |
|--------|------|---------|
| 密码、Token、密钥 | 安全风险 | 环境变量 |
| 会议录音/视频 | 体积大 | 链接到 Google Drive |
| node_modules | 工具依赖 | .gitignore 排除 |
| 个人笔记 | 非共享内容 | 个人文档 |

## 四、AI 交互规则

### 4.1 上下文加载

**不要一次加载所有文件**。按需加载：

| 任务 | 加载文件 |
|------|---------|
| 写新 PRD | 相关基线 + design.md + api-reference.md + prd-template.md |
| 生成原型 | PRD + design.md |
| 准备评审 | PRD + review-prep.md prompt |
| 合并基线 | iterations PRD + modules 基线 |

### 4.2 AI 输出要求

| 要求 | 说明 |
|------|------|
| 格式 | "按照 prd-template.md 格式输出" |
| 视角 | "产品视角，不要出现代码路径" |
| 术语 | "使用 glossary.md 中的术语" |
| 不确定 | "不确定的标注 ⚠️ 待确认" |
| 输出位置 | "保存到 iterations/v{x.y.z}/prd-xxx.md" |

### 4.3 AI 不应该做的事

| 禁止 | 原因 |
|------|------|
| 直接修改 modules/ 基线 | 基线仅在版本上线后由 Owner 合并 |
| 猜测 Figma 链接 | 必须由设计师提供 |
| 替代产品决策 | AI 提供选项和分析，PM 做决策 |
| 删除「⚠️ 待确认」标注 | 只有 PM 确认后才能移除 |
| 在 PRD 中写实现方案 | PRD 是产品文档，不是技术方案 |
