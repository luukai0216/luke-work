# PRD 输出格式规范（通用版）

## 文件命名

模块 PRD 文件统一存放于 `{output-dir}/modules/` 目录，命名规则：`{module-name-english}.md`

示例：`shopping-cart.md`、`user-auth.md`、`order-management.md`、`payment.md`

---

## 文档结构

每个模块 PRD 包含以下四个大章节：

### 一、文档元数据

```markdown
# {中文模块名} — {English Module Name}

---

## 一、文档元数据

| 字段 | 说明 |
|------|------|
| **项目名称** | {项目中英文名} |
| **模块名称** | {中英文} |
| **关联模块** | {本模块依赖或被依赖的其他模块，用自然语言描述} |
| **外部依赖** | {第三方服务、SDK、外部 API，用功能描述而非包名} |
```

紧接元数据表格后，包含三个子章节：

#### 截图/原型参考

表格形式列出所有相关的可视化资料。

```markdown
### 截图/原型参考

| 页面 | 截图 | 说明 |
|------|------|------|
| {页面名} | ![{描述}]({截图相对路径}) | {一句话说明} |
```

缺失截图标记为 `⚠️ 待补充`。

#### 设计稿索引

如果项目有 Figma/Sketch 等设计稿，统一指向索引文件。

```markdown
### 设计稿

> 本模块的设计稿统一维护在 [{设计稿索引文件}]({路径}) 的「{对应章节}」部分。
>
> 开发实现时以设计稿为**视觉标准**，本文档为**功能与逻辑标准**。如二者不一致，以设计稿最新版为准并同步更新本文档。
```

如无设计稿索引，可直接列出链接或标记为待补充。

#### 源码索引

折叠展示关键文件清单，便于 Dev 快速定位但不干扰产品阅读。

```markdown
### 源码索引（供 Dev 参考）

<details>
<summary>点击展开关键文件清单</summary>

| 类别 | 文件路径 | 说明 |
|------|---------|------|
| 页面 | `{path}` | {一句话说明} |
| 业务逻辑 | `{path}` | {一句话说明} |
| 服务层 | `{path}` | {一句话说明} |
| 状态管理 | `{path}` | {一句话说明} |

</details>
```

---

### 二、功能清单（Feature Inventory）

表格形式列出模块所有功能点。

```markdown
## 二、功能清单（Feature Inventory）

| # | 功能名称 | 功能描述 | 入口/触发方式 | 用户角色 | 优先级 | 状态 |
|---|---------|---------|-------------|---------|-------|------|
| F01 | {名称} | {一句话描述} | {用自然语言描述入口} | {用户角色} | P0-P3 | 已实现/部分实现/隐藏 |
```

优先级标准：
- **P0** = 核心链路（用户完成主要任务的必经路径）
- **P1** = 高频使用（大部分用户日常会用到）
- **P2** = 辅助功能（提升体验但非必需）
- **P3** = 边缘场景（少数用户或特殊条件下触发）

---

### 三、功能详细 Spec

对每个功能点（或相关功能合并），按以下结构输出：

```markdown
### F{编号}: {功能名称}

> **截图参考**：[{页面名}]({截图路径})
> **设计稿**：见 [{索引文件}]({路径})

#### 用户故事
> 作为**{用户角色}**，我希望{执行什么操作}，以便{达成什么目的}。

#### 前置条件
- {用户状态、网络状态、权限、数据依赖等}

#### 主流程（Happy Path）
1. 用户{操作}
2. 系统展示**{页面名称}**，包含以下内容：
   - {UI 元素 1}：{描述}
   - {UI 元素 2}：{描述}
   - ...
3. 用户{操作}
4. 系统{响应}
5. ...

#### 分支流程与异常处理

| 场景编号 | 触发条件 | 系统行为 | UI 表现 |
|---------|---------|---------|--------|
| E{功能编号}-01 | {触发条件} | {系统行为} | {用户看到的效果} |

至少覆盖以下类型：
- 输入校验失败（格式错误、超限、为空）
- 网络异常（超时、断网、服务不可用）
- 重复操作（防重复提交）
- 权限/状态不满足（未登录、无权限、功能未开启）
- 边界条件（空数据、超长文本、极端数值）

#### 业务规则

| 规则编号 | 规则描述 | 校验时机 | 失败处理 |
|---------|---------|---------|---------|
| BR-{前缀}{序号} | {规则描述} | {何时校验} | {失败时的处理方式} |

#### 数据依赖与接口清单（如有）

当功能涉及后端 API 或外部服务调用时：

| 接口名称 | 请求方式 | 端点 | 主要参数 | 返回内容 | 调用时机 | 缓存策略 |
|---------|---------|------|---------|---------|---------|---------|
| {业务语义名称} | GET/POST | /api/... | {关键参数} | {返回数据概述} | {页面加载/用户操作/定时刷新} | {缓存方式或无缓存} |

说明：
- **接口名称**：用业务语义命名（如「获取商品列表」），不用函数名
- **端点**：API 路径或 SDK 调用方式
- **调用时机**：明确是页面加载时、用户操作时、还是定时轮询
- **缓存策略**：说明数据是否缓存、缓存位置、刷新频率

#### 埋点事件（如有）
- `{event_name}` — {触发说明}
```

**重要写作规则：**

1. 主流程中**描述页面长什么样**，而不是「跳转到某组件」
2. 异常处理表格**不含代码位置列**
3. 分支流程用「情况 A / 情况 B / 情况 C」的自然语言描述，嵌入主流程中
4. 相关联的功能可合并为一个 Spec（如「注册」和「邮箱验证」）
5. **复杂分支逻辑配流程图**：分支 ≥3 个或涉及级联判断时，插入流程图 PNG

### 四、模块级总览

#### 4.1 页面流程

用**自然语言 + 缩进层级**描述页面跳转关系。格式示例：

```markdown
**起始判断：**
- 用户打开页面 → 系统检查登录状态
  - 未登录 → 进入**登录页**
  - 已登录 → 检查权限
    - 无权限 → 展示**权限申请页**
    - 有权限 → 进入**功能首页**

**{流程名称}：**
- {起始页} → 点击「{按钮}」→ **{目标页}**（{页面要素}）→ {操作} → **{下一页}**
  - 情况 A：{条件} → {走向}
  - 情况 B：{条件} → {走向}
```

#### 4.2 模块依赖关系

用**分组 + 文字描述**说明子模块和外部依赖，不用图表代码。

```markdown
**本模块包含 N 个子模块：**

1. **{子模块名}**：{包含页面} — {职责描述}
2. ...

**与其他模块的关系：**
- **{模块名}**：{如何交互}
- ...
```

#### 4.3 已知待优化项

```markdown
| # | 描述 | 影响 | 建议优先级 |
|---|------|------|----------|
| 1 | {问题描述，产品/用户体验视角} | {对用户的影响} | P1-P3 |
```

注意：从产品和用户体验角度描述，不是纯技术债。例如「支付失败时用户无明确提示」而非「catch 块为空」。

#### 4.4 迭代建议

```markdown
| 优先级 | 建议 | 原因 |
|-------|------|------|
| P1 | {建议内容} | {为什么重要} |
```

### 末尾：质量自检清单

```markdown
## 质量自检清单

- [x] 主流程步骤描述以用户视角和页面内容为主，无代码级实现描述
- [x] 异常流程覆盖了至少 5 种以上场景
- [x] 业务规则有明确的校验时机和失败处理方式
- [x] 截图/设计稿有引用或标记为待补充
- [x] 标注了所有不确定的点（⚠️ 需确认）
- [x] 待优化项从产品和用户体验角度提出
- [x] 源码索引折叠展示，不干扰产品阅读
```
