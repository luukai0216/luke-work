产品及 UI 组 AI 工作流规范

整合产品及 UI 组内的实践经验，定义产品经理与 UI/UX 设计师借助 Claude Code / AI 工具完成日常工作的标准流程、交付物要求和质量门禁。

Executive Summary

目标：让 AI 成为产品及 UI 团队的持续协作者，而非一次性工具。通过构建产品知识库，AI 在每次迭代中都能读取完整上下文，更快、更高质量地输出 PRD、原型、设计稿、评审报告，显著缩短从需求到交付的周期。

分工原则：AI 做信息收集、初稿生成和执行实现（80% 的重复劳动），人做产品判断、设计决策和最终验收（20% 的核心价值）。

一、核心原则

以下五条原则贯穿全部工作阶段，团队全员必须理解并遵守。

01
AI 做执行，人做决策
AI 负责信息收集、初稿生成、逐条检查、设计执行。PM 负责产品判断与优先级，设计师负责设计决策与品牌把控。AI 产出的一切内容都是草稿。
02
不允许脑补，信息不足先提问
AI 可能编造数据、杜撰接口。必须区分「已确认事实」「用户回答」「AI 推断」三类信息，严禁 AI 自行补完。
03
用文件沉淀，不用对话沉淀
对话会消失，文件可追溯。重要产出必须写入项目文件。每个环节的产出文件直接交付给下一环节，下游角色的 AI 可直接读取并继续推进，实现人 + AI 的接力式协作。CLAUDE.md 是项目的「长期记忆」，每次对话自动加载。
04
小步快跑，先骨架后内容
避免一次性让 AI 生成大量内容。先出骨架确认方向，再逐章填充细节。每轮对话聚焦一个明确目标。
05
链上变更成本高，提前想清楚
Web3 产品特有约束：合约部署后不可修改、链上交易不可逆、资产安全零容忍。涉及链上逻辑的需求必须在 PRD 阶段充分讨论异常场景和边界条件，安全审计前置，不可跳过。

二、工作流全景

工作流分为 7 个阶段，覆盖从需求到数据验证的完整闭环。每阶段完成后输出产物并等待 PM 确认，不自动推进。

适用范围：中型及以上需求（≥1 周开发量）走完整流程。小型需求（UI 微调、文案修改）可走简化流程。

2.1 需求调研与澄清

Phase 1把模糊需求变成结构化的、可执行的需求描述
双轨入口：已上线产品读取基线 PRD 做增量定义；从 0 到 1 从业务简报出发结构化定义范围。

AI 协作方式：

  1. 进入 Plan Mode（Shift+Tab）— 只分析不修改，PM 的安全网
  2. 苏格拉底提问法 — AI 分轮提问：问题真实性 → 方案合理性 → 成功衡量 → 约束取舍 → 战略合理性
  3. 多数据源调研（Web3 特色）— 链上行为数据 + 社区反馈 + 竞品分析 + 用户访谈

通过标准：

  • 需求的「为什么做」有数据或用户反馈支撑
  • 核心用户场景已识别（至少 3 个）
  • 成功指标已定义（可量化）
  • 约束和不做的范围已明确

产出：overview.md

2.2 PRD 撰写

Phase 2输出完整 PRD，回答「做什么、为什么做、做成什么样」
AI 读取基线 PRD + 设计规范 + 术语表 + API 参考，基于 12 章节模板生成初稿，PM 审阅修改。

PRD 12 章节结构：

1. 背景与目标
2. 目标用户与场景
3. 功能清单（P0/P1/P2）
4. 用户流程
5. 业务规则
6. UI / 交互说明
7. 异常场景与边界
8. 数据埋点需求
9. 国际化与文案
10. 兼容性与平台差异
11. 安全与隐私
12. 成功指标与验收
写作红线：PRD 不含代码/CSS 类名 · 不确定处标注「⚠️ 待确认」 · 异常场景写清错误码和文案，不接受模糊描述

产出：prd-{功能名}-v{N}.md + i18n-{功能名}.csv + tracking-{功能名}.csv

2.3 原型生成

Phase 3PRD 转化为可交互 HTML 原型
原型即文档 — 所有页面状态均需可见（弹窗、加载态、空态、错误态单独出图），让团队基于真实可操作的产品讨论。

状态覆盖要求：

状态说明是否必须
正常态数据正常展示必须
空态无数据时展示必须
加载态数据请求中必须
错误态请求失败/操作异常必须
边界态数据过长/极端值推荐

UI/UX 规范校验（强制门槛）：

校验项标准容忍度
色彩全部使用设计规范 token，零裸色值100%
字体字阶符合规范定义100%
圆角按钮/卡片/弹窗分别定义100%
间距 + 触控尺寸margin 符合规范 · ≥44px≥95%
总评分加权总分≥95% 方可评审

产出：prototype-{功能名}-v{N}.html + validation-{功能名}.md

2.4 AI 多角色预评审

Phase 3.55 角色 Sub-Agent 并行审查，提前拦截问题
在正式评审前，用 AI 模拟产品经理、前端、后端、设计师、QA 五个角色并行审查，减少评审返工。
Agent 角色审查重点
产品经理产品定位、需求完整性、优先级合理性、指标可衡量
前端开发交互可行性、组件复用、性能、浏览器兼容
后端开发架构合理性、数据流、API 设计、安全权限
设计师信息架构、UX 流程、一致性、视觉层次
QA 测试可验证性、边界条件、回归风险、文档准确性

输出分级： 🔴 P0 必须解决 🟡 P1 建议优化 🟢 P2 锦上添花

持续学习机制：每次真人评审后复盘 AI 预评审的命中/遗漏/误报，将经验追加到 CLAUDE.md，持续提升预评审质量。

产出：ai-review-{功能名}-{日期}.md

2.5 评审、交付与验收

Phase 4-6团队评审 → 开发跟进 → 上线验收
AI 预判评审挑战点并准备应答策略，人工面对面评审达成共识。开发阶段 PM 管需求变更，设计师管 UI 还原验收。

评审

  • 产品组内评审 → 跨职能评审（设计 → 开发 → QA），反馈记入 review-notes.md
  • 响应 SLA：需求歧义 2h 内、评审反馈 48h 内、紧急技术确认 4h 内
书面决策文化：所有重要决策必须书面存档。拒绝口头决策。

开发跟进

  • PM：PRD 作为 Single Source of Truth，提测后范围冻结，变更必须更新 PRD
  • 设计师：UI 还原度验收 ≥90%，走查反馈量化（设计稿值 vs 实际值），最多 3 轮

2.6 数据验证与持续迭代

Phase 7-8基线合并 → 数据验证 → 竞品对标 → 驱动下一轮迭代
版本上线后合并基线，用数据验证效果，结合竞品动态，形成「做 → 验证 → 改进」闭环。
版本效果复盘

漏斗 + 用户反馈

S1-S3设计准备：需求拆解 → 线框稿 → 规范校验
从 PRD 到可进入高保真设计的线框稿，中间插入强制规范校验门槛。

S1 需求拆解 — AI 读取 PRD 生成结构化设计简报（页面清单、组件清单、异常状态），设计师补充交互细节，使用「用户影响 × 开发复杂度」矩阵确认 MVP 范围，明确锁定「不设计的范围」。产出 brief-{功能名}.md，设计师 + PM 双签字。

S2 线框稿 — Claude 主导生成灰度 HTML 线框，设计师审核结构和信息层级。修改指令要精确：「改什么、改哪里、改成什么」。

S3 规范校验（强制门槛） — 线框稿进入高保真前必须通过校验，总分 ≥95%：

校验项标准容忍度
色彩 · 字体 · 圆角全部符合 design.md 定义100%
间距 · 触控尺寸margin 符合规范 · 可交互元素 ≥44px≥95%
不通过项必须一次性修复后重新校验，不允许带着不合规项进入 S4。
S4-S5设计执行：高保真 UI 稿 → 走查修改
设计师做「要不要」的决策，Claude 做「怎么做」的实现。走查反馈必须量化。

S4 UI 设计稿 — 在校验通过的线框稿上套用完整设计规范，生成高保真 HTML。关键检查：色差 deltaE < 2 · 图标线宽统一。产出 ui-{功能名}-v{N}.html

S5 走查修改 — 走查反馈必须量化，不接受「感觉不对」。使用标准表格（ID / 页面 / 问题 / 期望效果 / 优先级）。每处修改标注走查 ID。

走查最多 3 轮。超过 3 轮说明 S1 需求拆解不清晰，需回退补充简报。
S6-S7交付验收：开发交付包 → 还原度验收
AI 从代码直接提取 CSS 数值生成标注文档（无手工误差），截图对比验收还原度。

S6 交付包 — 交付物：终版 HTML 设计稿 + Figma 设计稿链接 + Markdown 标注文档（CSS Token、组件尺寸、动画参数） + 切图清单 + 可复用 components.css。标注使用工程语言（CSS 属性和值）。

Figma → 代码：设计师交付 Figma 链接后记入 figma-design-index.md 或迭代版本目录下的 figma-mapping.md。开发可通过 Figma MCP 让 Claude Code 直接读取 Figma 设计稿的布局、组件、Token 和样式信息，自动生成高还原度的前端代码（HTML/CSS/React），大幅减少手工还原偏差和反复走查的成本。

S7 开发验收 — 设计稿值 vs 开发实现值逐项对比：

严重程度标准处理方式

验收通过：整体还原度 ≥90%，设计师签字。产出 acceptance-{功能名}-{日期}.md

文档协作与同步

当前方案：Google Drive（过渡）

当前阶段使用 Google Drive 作为团队共享和备份方案。每次同步通过 sync-drive Skill 触发，同步前自动在本地创建全量 .zip 备份。

规则说明
谁触发通过 sync-drive Skill 触发，AI 不主动同步
同步方向本地 → Drive（单向），Drive 不回写本地
本地备份每次同步前自动在本地创建全量 .zip 备份，存入 _backup/
同步范围.md / .csv / .html / 图片，排除 node_modules
为什么本地备份？ Google Drive 对非 Google 格式文件（.md / .html / .csv）需要手动「管理版本 → 保留此版本」才能下载旧版本，实际操作中容易遗漏。本地全量 .zip 备份解压即可一步恢复。

协作模式：

  1. PM / 设计师在本地（Claude Code）编辑文档
  2. 通过 sync-drive Skill 同步到 Drive（自动本地备份）
  3. 团队通过 Drive 查阅和评论
  4. 反馈通过评审会收集，PM 在本地处理后重新同步
角色Drive 权限说明
PM / 设计师（文档 Owner）编辑通过 Skill 同步更新
开发 / QA查看 + 评论通过评论反馈，不直接编辑
PM Lead编辑紧急情况下可直接修改

目标方案：Git 知识库（推荐演进方向）

建议后续将知识库迁移到 Git 仓库（如 GitLab），实现更专业的版本管理和协作。

维度Google Drive（当前）Git 仓库（目标）
版本管理手动备份 .zip，粗粒度每次提交精确 diff，完整历史
协作评论 + 口头反馈MR/PR Review，评论绑定具体行
变更追溯靠备份文件名推断git log / git blame 精确到行
分支管理不支持版本分支、并行开发
与 Claude Code 集成需手动触发 Skill原生集成，天然协作
权限管理文件夹级别仓库/分支/目录多级控制

为什么不用 Confluence？

Confluence 作为传统文档平台可以满足一般协作需求，但在 AI 协作工作流中存在两个核心限制：

  • AI 读写友好度不足 — Confluence 的富文本存储格式与 AI 原生的 Markdown 工作流不匹配，AI 直接读写 Confluence 页面时需要额外的格式转换层，增加复杂度和出错概率
  • 格式兼容性损失 — Markdown 与 Confluence 富文本互转时，表格、代码块、嵌套列表、折叠标签等格式经常出错或丢失，PRD 这类结构化文档的还原度不高
本地 Markdown 文件是 AI 协作的最佳载体：CLAUDE.md 自动加载、Skill 直接读写、格式零损耗。

六、质量门禁

PRD 八项检查（每份 PRD 提交前必过）

  • 目标清晰：一句话说清「为什么做」
  • 范围明确：功能清单有 P0/P1/P2 标注
  • 用户流程完整：主流程 + 分支 + 异常
  • 状态覆盖：正常/空/加载/错误态均有描述
  • 边界覆盖：极端值、并发、权限等场景
  • 验收标准可检查：每条标准可判断「通过/不通过」
  • 无歧义：无模糊表述、无冲突、无不可执行的描述
  • 内审结论已记录：AI 预评审报告已处理

上线前 PM / 设计师检查（发版前必过）

  • PRD 所有 P0 功能点已实现
  • 核心流程端到端走通
  • UI 还原度 ≥90%（设计师签字）
  • 文案与 PRD 一致（中英文均检查）
  • 空态/加载态/错误态展示正确
  • 需求变更已同步更新 PRD

AI 常见陷阱

陷阱表现规避方法
编造数据AI 自行补充转化率、用户量要求标注数据来源，假设数据标注「假设」
杜撰接口AI 虚构不存在的 API与 api-reference.md 交叉验证

裸色值原型使用硬编码色值而非 token强制规范校验门槛

流程常见错误

错误后果正确做法
跳过 Plan Mode需求理解偏差导致返工先进 Plan Mode 对话确认需求
