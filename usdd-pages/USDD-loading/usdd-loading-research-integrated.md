# USDD · Loading Research & Design Proposal

**整合日期：** 2026-04-02
**研究对象：** `USDD` · https://usdd.io · App: https://app.usdd.io  
**参照对象：**

- `USDS / Sky` · https://sky.money · App: https://app.sky.money
- `USDe / Ethena` · https://ethena.fi · App: https://app.ethena.fi
- `Spark` · https://spark.fi · App: https://app.spark.fi
- `USDC` · https://circle.com/usdc
- `Uniswap` · https://uniswap.org · App: https://app.uniswap.org

- `Aave` · https://aave.com · App: https://app.aave.com

> 本文档分两部分：竞品分析回答"行业怎么做、USDD 差在哪"，设计建议回答"应该怎么改、改到什么程度"。顺序为先分析、再归纳、再给方案。

- `USDC` 为营销官网，适合作为"首屏与静态内容加载"参照，不适合作为复杂 DeFi App 参照。

Something went wrong`，以及数据抓取失败时仅做控制台容错。有基础失败处理，但更多停留在营销站和脚本层，不是产品化异常系统。 | 证据最明确：页面源码直接暴露 `global-error`、`not-found`、`Access Restricted`、`Page Not Found` 和 `Retry`，页面级异常和可重试错误已建立明确边界。 | Bundle 中同时存在 `retry / empty / error / Error / Empty`，覆盖面广，不只处理整页失败，也对局部数据失败和空状态做了组件级区分。 | 公开证据集中在实验脚本、表单和前台错误容错（如 `anti-flicker` 兜底），有异常保护，但重点不在数据模块级异常设计。 | 公开 bundle 包含 `ErrorBox`、`LoadingState`、`LoadingSkeleton` 及多个错误 / 失败流程屏文件名，页面级与模块级异常之间有明确分层。 | 路由层存在 `notFound` / `error` 承接位，产品配置有 `manualServiceUnavailable`、`updatesInProgress` 等服务级开关，预留了页面级异常和服务降级入口。 | 公开入口未找到足够强的异常组件证据，保守判断为有成熟产品常见的基础错误处理，但无法确认异常分层细节。 | 结论不是"补一个错误页"，而是"先建立异常分层"。明确三层：整页不可用 → 页面级异常；单接口失败 → 模块内错误 + Retry；接口成功无内容 → Empty。三层边界清晰，异常体验才可信。 |

## 3. 核心结论

按加载设计成熟度，8 个对象大致分三档：

- 第一梯队：`Morpho`、`Uniswap`、`Spark`、`Ethena`
- 第二梯队：`Aave`、`Sky`、`USDC`
- 当前 `USDD`：功能已上线，加载体验未系统化

USDD 的问题不是完全缺少加载态，而是还没形成系统：

1. 首屏缺少页面框架，用户容易感知为空白等待。
2. 数据加载缺少统一占位语言，不同模块状态表达不一致。
3. 操作 loading 缺少层级划分，按钮、模块、流程之间没有规范。
4. 异常设计公开证据较弱，接口级异常与空状态分层不清晰。

USDD 现在是"有零件"，但还没有形成完整的 loading design system。

## 4. USDD 当前状态拆解

USDD 当前加载状态可拆成四段：

```text
用户进入任意页面
        │
        ▼
① 全站样式 + 静态内容加载
        │
        ▼
② 数据、图表、表格等从接口加载
        │
        ▼
③ 用户操作触发异步过程
        │
   （可能出现）
        ▼
④ 页面失败 / 接口失败 / 操作失败 / 空状态
```

对应问题：

- 第①段：当前容易出现黑底空等待。
- 第②段：部分地方有占位，部分地方直接消失、显示 `0` 或跳变。
- 第③段：操作 loading 反馈不统一。
- 第④段：整页异常与局部数据异常没有完全分层。

---

## 5. 设计目标

1. 用户在任意等待阶段，都知道"系统正在做什么"。
2. 页面在加载过程中始终保持稳定布局，不闪、不塌、不误导。
3. `loading`、`empty`、`error` 三类状态边界清晰，不能混用。
4. 所有 loading 体验优先服务于可信赖感，而不是动效。

---

## 6. 设计方案

### 6.1 首屏加载

首屏采用"品牌加载壳 + 真实布局骨架"方案，不单独放 Spinner。

```text
进入页面
   │
   ▼
品牌背景 / Logo
   │
   ▼
导航骨架 + Hero 骨架 + CTA 骨架 + 数据卡骨架
   │
   ▼
真实内容替换进入
```

#### 推荐方案

- 先出现品牌底色 / 渐变背景。
- Logo 先出现，建立品牌识别。
- 同时渲染导航骨架、Hero 骨架、CTA 骨架、数据卡骨架。
- 整体节奏控制在 300~500ms，避免一闪而过，也避免长时间停留。

#### 设计原则

- 不允许空 root 直接等待。
- 不做重品牌开场动画，优先轻量淡入 + shimmer。
- 骨架必须贴近真实布局，避免加载完成后版式重排。

#### 可选层级

| 方案 | 描述 | 适用性 |
| --- | --- | --- |
| A | 品牌 Logo + 脉冲 / 三点动效 | 开发最轻，适合快速落地 |
| B | 顶部进度条 + 简化品牌壳 | 最轻量，适合短期补齐 |
| C | 页面真实骨架 + shimmer | 体验最好，推荐正式方案 |

---

### 6.2 接口数据加载

数据加载统一拆为三类：数字类、图表类、表格类。三类均使用骨架条样式，不要用单一 loading 处理所有内容。

```text
接口请求开始
   │
   ├─ 数字类 -> 骨架条
   ├─ 图表类 -> 骨架条（固定高度容器内堆叠）
   └─ 表格类 -> 骨架条（逐行排列）
   │
   ▼
数据返回后原位替换
```

#### 数字类

适用于 TVL、APY、Supply、Debt、收益额等。

- 使用与真实数字尺寸接近的骨架条。
- 不显示 `0`，不显示 `...`，不让文字缩成 `0px` 消失。
- 骨架条锁定高度和宽度，避免请求完成后布局跳变。

#### 图表类

适用于折线图、面积图、分布图等。

- 图表容器固定高度，内部用多行骨架条模拟图表结构（如高低错落的横条）。
- 不用 Spinner 替代图表区域，骨架条能更好地撑住布局、减少跳变感。
- 骨架条宽度可按图表轴方向做适当变化，增加辨识度，但不要过度设计。
- 加载完成后图表淡入替换骨架条，避免整块突然切换。

#### 表格类

适用于资产列表、Collateral List、历史记录等。

- 表头保持真实显示，不用骨架条替换列标题。
- 表体每行按列宽显示骨架条，4~6 行占位，行高与真实内容行一致。
- 每列骨架条宽度参考该列实际内容宽度（数字列窄、名称列宽），避免所有列等宽显得失真。
- 不建议整张表只放一个 Spinner，会让整个数据区塌陷。

### 6.3 操作反馈 Loading

```text
用户点击异步操作
   │
   ├─ 按钮级 -> 按钮 loading
   ├─ 模块级 -> 当前卡片 / 表格 loading
   └─ 流程级 -> 独立处理中界面
   │
   ▼
过程完成后返回原界面
```

#### 设计原则

- 跳转型按钮不需要复杂 loading。
- 异步操作型按钮必须有明确 loading。
- 按钮 loading、模块 loading、流程 loading 需有层级差异。

#### 按钮 loading

适用于 `Estimate Earnings`、`Mint USDD`、`Migrate USDD`、`Redeem`、`Deposit` 等。

- 点击后按钮进入 loading 状态，背景和尺寸保持不变。
- 左侧显示转圈图标，文案改为进行中表达，如 `Estimating...`。
- loading 期间禁止再次点击。

#### 局部模块 loading

适用于某张卡片、某个图表、某个表格块单独刷新。

- 只影响当前模块，不拖累整页。
- 保留模块边界和标题。
- 模块内切换为骨架条占位。

#### 流程 loading

适用于钱包连接、链上提交、交易处理中等多步骤场景。

- 不只让按钮转圈，进入明确的处理中界面，告诉用户当前步骤正在执行。
- 参考 Uniswap 和 Morpho 的结构化 loading 方式。

### 6.4 加载异常设计

#### 整页级异常 · 404 Not Found

**触发场景**

- 用户输入了不存在的路径，如 `app.usdd.io/xyz`
- 外部链接已失效或路由被重命名
- App 内跳转时目标资源已删除或下线

**与 500 / 断网的区分**

| 状态 | 原因 | 用户可自行解决 | 主操作 |
| --- | --- | --- | --- |
| 404 | 路径不存在 | 是（回去就行） | 返回首页 / 上一页 |
| 500 | 服务端错误 | 否（等修复） | 稍后再试 / 刷新 |
| 断网 | 网络中断 | 是（检查网络后重试） | 重试 |

404 是"你来错地方了"，不是"系统坏了"。文案和视觉情绪应中性偏引导，不给用户压迫感。

**页面结构**

```text
导航栏（保留，用户可直接跳转其他页）
   │
品牌 Logo（保持识别感）
   │
404 提示区
   ├─ 状态标识：数字 "404" 或图形（非必须）
   ├─ 主标题：一句话说明情况
   ├─ 副文案：给出建议行动
   └─ 主操作按钮：返回首页
        （可选）次操作：回到上一页
   │
页脚（可选，轻量）
```

**文案建议**

- 主标题：`Page Not Found`（国际化首选）或 `找不到该页面`
- 副文案：`The page you're looking for doesn't exist or has been moved.`
- 主按钮：`Back to Home`
- 次按钮（可选）：`Go Back`

避免写成：
- `Oops! Something went wrong.`（这是 500 的语气，404 不是系统故障）
- `Error 404`（过于技术，用户无感知）
- 只展示数字而不给出任何跳转入口

**视觉原则**

- 整体轻量、中性，不要做成警告红或故障感。
- 插画可选，如使用应与 USDD 品牌调性一致，不建议用通用卡通 404。
- 导航栏必须保留，用户不应感到被系统踢出产品。
- 404 页面本身是最终状态，不允许出现任何数据加载 loading。

**与其他页面的衔接**

- 404 不应触发全局错误弹窗叠加。
- 不需要自动重试（路径不存在，重试没意义）。
- 从 App 内跳转触发时，"Go Back" 应是有效的返回操作。

## 7. 建议的状态流转

```text
Loading
  ├─ Success
  ├─ Error
  └─ Empty

Error
  └─ Retry -> Loading
```

对于操作型按钮：

```text
Default -> Loading -> 恢复
                └-> 若失败，错误提示独立承接，按钮回到默认
```

核心原则：

- `Loading` 只表达"正在进行"
- `Error` 只表达"失败"
- `Empty` 只表达"无数据"

三者不能混用。
