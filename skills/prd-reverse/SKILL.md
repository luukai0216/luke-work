# 逆向 PRD 生成（通用版）

## 概述

从任意项目的源代码和现有资料（设计稿、旧文档、Wiki、截图等）逆向生成结构化的产品需求文档（PRD / Functional Spec）。

**适用范围：**
- 前端项目（Web/Mobile/Extension/小程序）
- 后端服务（API/微服务）
- 全栈项目
- 不限定语言和框架

**文档受众：** QA 工程师、前端/后端开发、UI/UX 设计师、产品经理。

## 前置配置

使用前需要告诉 Skill 以下信息（通过参数或项目配置文件）：

| 配置项 | 说明 | 示例 |
|-------|------|------|
| **项目名称** | 项目中英文名称 | TronLink / MetaMask / 我的电商平台 |
| **源码位置** | 源码根目录路径 | `/path/to/project/src/` |
| **输出位置** | PRD 文档输出目录 | `./prd/modules/` |
| **现有资料位置**（可选） | 设计稿/旧文档/截图等 | `./docs/`, `./screenshots/` |
| **技术栈提示**（可选） | 帮助 Skill 更准确定位代码 | React + TypeScript + Redux |

### 项目配置文件（可选）

可在 PRD 输出目录下创建 `project-config.md` 来持久化配置：

```markdown
# 项目配置

| 字段 | 值 |
|------|---|
| 项目名称 | {项目名} |
| 源码根目录 | {路径} |
| PRD 输出目录 | {路径} |
| 截图目录 | {路径} |
| 设计稿索引 | {路径或链接} |
| 技术栈 | {语言 + 框架 + 状态管理等} |
| 代码组织方式 | {按功能/按层/Monorepo等} |
```

## 使用方式

### 生成新模块 PRD

```
/reverse-prd 项目：{项目名} 源码：{源码路径} 模块：{模块名称} 代码范围：{目录或文件}
```

示例：
```
/reverse-prd 项目：我的电商App 源码：/code/ecommerce/ 模块：购物车 代码范围：src/pages/cart/
```

### 使用已有配置

如果已创建 `project-config.md`，可简化为：
```
/reverse-prd 模块：购物车 代码范围：src/pages/cart/
```

### 更新已有模块中的某个功能

```
/reverse-prd 更新模块：{模块名} 功能：{功能编号或名称}
```

### 补充新功能 Spec

```
/reverse-prd 补充模块：{模块名} 新功能描述：{功能概述}
```

### 基于现有资料整理

```
/reverse-prd 模块：{模块名} 资料来源：{文件路径/目录} 类型：{旧文档/设计稿/Wiki导出}
```

## 执行流程

### 第一步：解析项目结构

1. 读取项目配置（如有 `project-config.md`）
2. 使用 Agent (Explore) 扫描项目目录结构，识别：
   - 代码组织方式（按功能模块 / 按技术层 / Monorepo）
   - 技术栈（语言、框架、状态管理、路由方案）
   - 代码分层（页面/组件/服务/状态/模型/工具）
3. 定位指定模块的所有相关文件

**通用文件分类参考：**

| 类别 | 常见位置模式 | 关注点 |
|------|------------|--------|
| 页面/视图 | `pages/`, `views/`, `screens/`, `routes/` | UI 结构、用户可见内容 |
| 组件 | `components/`, `widgets/` | 可复用 UI 单元 |
| 业务逻辑 | `hooks/`, `composables/`, `controllers/`, `blocs/` | 核心业务流程 |
| 服务层 | `services/`, `api/`, `repositories/` | 数据获取、外部交互 |
| 状态管理 | `store/`, `redux/`, `providers/`, `models/` | 数据流转 |
| 类型/模型 | `types/`, `interfaces/`, `models/`, `entities/` | 数据结构 |
| 常量/配置 | `constants/`, `config/`, `enums/` | 业务规则、枚举值 |
| 工具函数 | `utils/`, `helpers/`, `lib/` | 辅助逻辑 |

4. 产出文件清单，确认代码范围

### 第二步：阅读源代码

1. 并行读取所有关键文件（通过多个 Agent 并行提高效率）
2. 重点关注：
   - **页面/视图层**的 UI 结构 → 推导页面内容和布局
   - **业务逻辑层**的处理流程 → 推导主流程、分支、校验规则
   - **服务层**的接口调用 → 推导 API 依赖和数据流
   - **状态管理**的数据结构 → 推导数据模型和状态流转
   - **常量/枚举** → 推导业务规则和约束
   - **错误处理和用户提示** → 推导异常流程
   - **埋点/监控调用** → 推导埋点事件清单

3. **接口依赖梳理**：
   - 定位 API 调用文件（service / api 层）
   - 追溯数据流：哪些数据来自 API、哪些来自本地
   - 记录接口的请求方式、参数、响应、调用时机、缓存策略

### 第三步：整合现有资料

1. 检查是否有可用的现有资料：
   - 截图 / 原型图 → 在 PRD 中引用
   - 旧文档 / Wiki → 提取有效信息，补充到 PRD
   - 设计稿链接 → 维护索引
   - 用户反馈 / 测试报告 → 补充已知问题
2. 截图可用则引用，缺失则标记 `⚠️ 待补充`
3. 旧文档中的业务上下文优先保留（如产品决策背景、历史原因说明）

### 第四步：生成 PRD

按照 [references/output-format.md](references/output-format.md) 规定的格式输出。

### 第五步：为复杂分支逻辑生成流程图

1. 识别模块中包含 ≥3 个分支判断的复杂逻辑
2. 用 Mermaid flowchart 语法编写，生成 HTML 后用 Playwright 渲染为 PNG
3. 保存到 `{output-dir}/flowcharts/{name}.png`
4. 在 PRD 中引用：`![描述](flowcharts/{name}.png)`
5. 流程图使用中文标签，判断用菱形，成功绿色、失败红色、判断橙色

**适合加流程图的场景：**
- 多条件分支判断（≥3 种不同流程）
- 级联状态检查
- 涉及自动选择/降级的逻辑
- 多步骤验证/审批流程

**不需要流程图的场景：**
- 线性主流程 — 用编号步骤即可
- 简单二选一判断 — 用文字说明即可

### 第六步：更新设计稿索引（如适用）

如果项目维护了设计稿索引文件，为新模块添加对应条目。

## 写作原则

### 必须遵守

1. **产品视角**：用自然语言描述页面内容和交互行为，不写组件名、路由名、函数名
   - 错误：「系统跳转至 CartPage 组件」
   - 正确：「系统展示购物车页面，包含以下内容：...」

2. **忠于代码**：所有描述基于实际代码，不臆测。逻辑不清晰处标注「⚠️ 需确认」

3. **描述页面内容**：每个页面的主流程中，必须列出 UI 元素（标题、输入框、按钮、提示文案等）

4. **流程用自然语言**：用缩进层级 + 箭头描述页面跳转关系，不用 Mermaid 代码

5. **异常覆盖全面**：每个功能至少覆盖 5 种以上异常场景（输入校验、网络异常、重复操作、权限不足、边界条件）

6. **源码索引折叠**：保留关键文件清单但放在 `<details>` 标签中，不干扰产品阅读

7. **保留业务上下文**：如果现有资料中有产品决策背景、历史原因等信息，在 PRD 中保留

### 不要做

1. 不要写「数据模型与状态流转」章节（TypeScript interface、Mermaid stateDiagram）
2. 不要在异常处理表格中加「对应代码位置」列
3. 不要在功能 Spec 正文中出现文件名、函数名、变量名
4. 不要用 Mermaid 代码块画流程图（用渲染后的 PNG）
5. 不要给出时间估计
6. 不要臆造不存在的功能或流程

## 质量自检

生成 PRD 后，必须逐项确认：

**基础规范：**
- [ ] 主流程步骤以用户视角和页面内容为主，无代码级描述
- [ ] 每个功能点的异常流程覆盖至少 5 种场景
- [ ] 业务规则有明确的校验时机和失败处理方式
- [ ] 截图/设计稿有引用或标记为待补充
- [ ] 所有不确定的点标注了「⚠️ 需确认」
- [ ] 待优化项从产品和用户体验角度提出
- [ ] 源码索引折叠展示

**Review 经验（避免踩坑）：**
- [ ] **前置拦截页面**：检查流程入口是否有前置页面（用户协议、安全警告、权限申请等）
- [ ] **功能清单 vs Spec 覆盖一致**：清单中每个功能点要么有完整 Spec，要么有交叉引用
- [ ] **跨功能机制单独说明**：贯穿多页面的全局行为（如权限校验、登录态检查）要独立描述
- [ ] **多端/多环境差异显式对比**：涉及不同平台或环境行为差异的，用对比表格说明
- [ ] **数据依赖/接口清单完整**：每个有外部数据交互的模块都要列出接口
- [ ] **页面描述与截图/设计稿对齐**：UI 元素描述要与可视化资料一致
